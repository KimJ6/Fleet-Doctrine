# FleetDoctrine — 2단계 전투 아키텍처 및 컴퓨터그래픽스 적용 참고 명세

> **문서 상태:** 작성 당시의 전투·CG **참고 설계**. 2단계 설계는 [데이터·사건 중심 상세 재설계](phase2-data-oriented-combat-design.md), 현행 단계 범위는 [구현 계획](implementation-plan.md), 게임 규칙은 [v2.2 기획](../spec/game-design-v2.2.md)이 우선한다. 구현이나 검증 완료 선언이 아니다.  
> **작성일:** 2026-11-23  
> **프로젝트:** [KimJ6/Fleet-Doctrine](https://github.com/KimJ6/Fleet-Doctrine) (three.js 기반 웹 프로토타입)  
> **핵심 목표:** 2단계 「명령 유지 사격과 실제 전투 한 구간」에 필요한 **Body/Weapon 분리, 함대 단위 후보 탐색, 정확한 3D 무장 좌표 변환, 3D 투사체 명중 판정**을 연결하고, 수업 개념의 직접 구현·확장과 검증 증거를 남긴다.

## 0. 필독: 우선순위와 출처 구분

### 0.1. 문서 우선순위

1. **게임 규칙의 최상위 기준:** `docs/spec/game-design-v2.2.md`.
2. **현행 단계 구분:** [구현 계획](implementation-plan.md). 2단계에는 전장·득점도 포함한다. 이 참고 설계의 원래 범위와 단계 번호는 작성 당시 제안이며, 공격·피격 처리에서 새 상세 재설계와 충돌하면 새 설계를 따른다.
3. **구현·에셋 실제 상태:** `web/`, `rigging-test/`, `README.md`, `docs/policies/ship-rigging.md`를 코드 기준으로 재확인.
4. **아키텍처 참고 출처:** 사용자 제공 `OverTheHorizon_다진영_대규모전투_아키텍처_설계초안.md` (revision 0.1, `proposal_not_canonical`, **design_only**). 이 문서의 원칙을 **선택적으로 번안**하며 Unity ECS 관련 세부 구현을 FleetDoctrine에 강제하지 않는다.
5. **강의 근거:** W08L1, W09L1, W10L1, W11L1 원본 PDF. 페이지는 **PDF 페이지 기준**으로 표기한다.

### 0.2. 표기 규칙

- **[확정 — v2.2]** 사용자 승인 게임 규칙. 하위 설계가 변경 불가.
- **[기존 코드에서 확인]** 2026-11-23 저장소 `main`의 소스/README로 확인 가능한 사항. 테스트 통과·전체 통합 완료를 뜻하지 않는다.
- **[참조 아키텍처]** OverTheHorizon 초안의 설계 주장. FleetDoctrine의 확정 계약은 아님.
- **[2단계 권장]** 과제와 구현 규모를 고려한 새 설계 선택.
- **[후속 검토]** 성능/정확성 데이터 확보 후 결정.
- **[미결]** 사용자 결정 또는 추가 검증이 필요한 내용. 숫자는 특정하지 않는다.

이 문서의 타입·모듈명·함수명은 **개념적 인터페이스 이름**이다. 기존 파일·클래스가 이미 동작할 때는 중복 구현하지 말고 기존 소유권과 맞춰 변경한다. 문서에 포함된 의사코드는 완성된 라이브러리 코드나 확정 API가 아니다.

### 0.3. 게임 규칙 불변식: 구현 중 훼손 금지

1. 이동 명령은 `MOVE`(목적지 이동), `PATROL`(경로 순찰) **2개**; 교전 대응은 `OPPORTUNISTIC_FIRE`(명령 유지 사격), `STANDOFF`, `BREAKTHROUGH`, `ENCIRCLE`, `POINT_DEFENSE` **5개**이다. 새 독립 정책을 발명하지 않는다.
2. 2단계 핵심인 `OPPORTUNISTIC_FIRE`는 **함대 기준 이동 목표·경로·대형·함대 진행 방향을 적 추적 때문에 변경하지 않는다**. 사격 불가능하면 사격하지 않는다. 개별 함선의 조준 회전 허용 범위·이동 추종 우선순위는 v2.2 §10.5의 **미결**을 침범하지 않는다.
3. 함대 기준 자세와 개별 함선 선체·포탑 자세는 분리한다. 같은 높이의 적과 싸워도 필요한 Pitch/Roll을 일률적으로 금지하지 않는다. 비전투 대기에는 함대가 수평 정렬로 복귀한다.
4. 플레이어 명령 좌표만 3D 격자 교차점으로 입력한다. 함선·포탄·진형 슬롯·자동 전술 목표는 **연속 3D 월드 좌표**다.
5. 대형은 독립 명령이 아닌 기존 정책의 결과다. 함선이 표적을 추적하면서 임의로 슬롯을 이탈하지 않는다.
6. v2.2의 최종 게임 목표는 **9개 득점 구역, 현재 보유 점수 승리, 동일 점수로 함선 구매·증원**이다. **적 전멸은 즉시 승리가 아니다.** 2단계에서는 전멸을 전투 테스트 사건으로 사용해도 승리 상태로 잘못 연결하지 않는다.
7. 준비 단계는 시뮬레이션 정지이며 위치·방향·체력·발사체·재장전·진형/조우 진행 상태를 보존한다. v2.2의 득점은 전투 시뮬레이션 시간에만 진행한다.

## 1. 적용 배경: 현행 코드와 요구 작업의 경계

### 1.1. 검토한 현행 경로

| 경로 | 확인한 책임/상태 | 2단계 연결 시 주의 |
|---|---|---|
| `web/simulation.js` | 명령 격자와 함대·함선 위치, Quaternion, 슬롯, 이동/도착 처리 | 이동 상태를 무장 코드가 직접 수정하지 않게 함 |
| `web/main.js` | 원근 관람 카메라, XZ→YZ 직교 입력, 화면·선택·시각화 | 입력용 Raycaster를 전투 충돌/명중 근거로 재사용하지 않음 |
| `web/minimap.js` | 스타터 데모용 별도 미니맵 코드 | 현재 함대 게임은 `web/main.js`의 2D 캔버스 미니맵을 사용한다. 기존 코드를 게임 구현 증거로 혼동하지 않음 |
| `rigging-test/rig-control.js` | FBX 피벗 탐색, 무장별 축·회전 범위·자세 제어 | 자산별 로컬 축/회전 부호를 게임 공통 좌표계와 구분 |
| `rigging-test/rig-safety.js` | `three-mesh-bvh` 기반 메시/리깅 안전 검사 | 외부 BVH 라이브러리 사용 ≠ 직접 만든 BVH. 매 전투 틱 적용을 전제하지 않음 |
| `docs/design/implementation-plan.md` | 단계 2를 명령 유지 사격·발사·피해·전투 구간으로 정의 | v2.2 기준 재계획에 따라 현행 범위와 수용 기준 확인 |

**현행 검증 범위:** 저장소에서 해당 코드와 문서의 존재·구조를 확인했다. 이 문서는 브라우저 실행, 모든 FBX 테스트, 성능 측정을 직접 완료했다고 주장하지 않는다. 실제 구현 전 현재 커밋과 파일 변경 여부를 다시 확인한다.

### 1.2. 2단계의 완료 정의 [2단계 권장]

- `MOVE`가 동작 중이어도 `OPPORTUNISTIC_FIRE`의 유효 무장이 적을 선택해 **실제 포구**에서 발사한다.
- 회전식 포탑과 고정식 무장이 서로 다른 사격 범위를 지킨다.
- 선체·장착점·포신의 좌표 변환과 투사체의 3D 이동·명중·피해가 **동일한 권위 시뮬레이션 틱**에서 일관되게 계산된다.
- 명중과 격침의 논리는 렌더링 효과와 분리한다.
- 전투 시간이 끝나면 준비 단계로 돌아가고, 재개 후 체력·위치·쿨다운·기존 탄체가 유지된다.
- 수업에서 배운 **하나 이상**의 CG 기법을 직접 구현/확장해 원리·검증·기여를 설명할 수 있다. 이 문서는 **W08 변환과 W10 경계 볼륨/교차**를 핵심 후보로 제안한다.
- **당시 범위 제안:** PATROL, 공동 화력 최적화, 다른 4개 교전 대응, 상점·점수 완성, 규모 최적화를 후속으로 두었다. 현행 계획은 2단계에 기본 득점과 현재 점수 승리를 포함하며 구매·증원은 3단계에 둔다. 다만 이 기능들을 최종 게임 기획에서 삭제한 것으로 취급하지 않는다.

## 2. OverTheHorizon 설계의 선택적 이식

### 2.1. 개념 대응표

| OverTheHorizon 초안 | FleetDoctrine에서의 대응 | 처리 |
|---|---|---|
| `Faction` | `team`: 플레이어/적군 | **직접 번안**. 외교/중립 확장 금지 |
| `TacticalGroup` | 함대 `Fleet`; `ENCIRCLE` 시 임시 네 분견대 | **직접 번안** |
| `CombatBody` | `Ship`의 이동·회전·체력·생존 | **직접 번안** |
| `WeaponMount` | 선체 상대 포탑·포신·고정포와 재장전 | **직접 번안** |
| `GroupTacticalPlan` | 함대 명령 + 현재 조우/적군 후보 + 진형 목표 | **기존 Fleet 명령 구조 재사용** |
| Faction-neutral Spatial Source | 양측이 공유하는 적 후보 탐색 서비스 | **인터페이스 우선**, 인덱스는 후속 검토 |
| `GroupContact` | 함대의 유효 후보 ID·조회 틱 | **필요한 경우만** 작은 버퍼 도입 |
| `AssignedTarget` / `FireEligible` / `Hit` | 배정·발사 가능·실제 명중 | **서로 다른 판단**으로 구현 |
| Stable Resolve / Host Commit | 한 로컬 시뮬레이션이 피해·격침을 단일 확정 | **단순화해 차용**. 네트워크 불필요 |
| Unity Entity/Jobs/Burst/ECB/Netcode | 해당 없음 | **이식하지 않음** |
| Adaptive Planner / 글로벌 Contact Graph / Simulation LOD | 규모에 따른 최적화 후보 | **초기 제외** |

**전술 그룹과 공간 셀을 혼동하지 않는다.** 함대·분견대는 지휘 소속이고, Spatial Cell은 검색 최적화 단위이다. v2.2의 **9개 득점 구역**도 이들과 완전히 다른 게임 규칙 판정 영역이다.

### 2.2. 논리적 책임 흐름

```text
[BattleState: 단일 권위 데이터]
          |
          +--------------------------+
          |                          |
          v                          v
 [Fleet Command/Plan]        [Combat Candidate Source]
          |                          |
          +-----------> [후보/표적 배정] <-----------+
                           |
               +-----------+-----------+
               |                       |
               v                       v
        [Ship Body Movement]      [Weapon Aim/Ready]
               |                       |
               +------------+----------+
                            |
               [같은 틱 Muzzle Pose 확정]
                            |
                   [Projectile/Hit]
                            |
                    [Damage/Death]
                            |
                 [Score/Win: v2.2 후속]
                            |
                 [Visual/HUD/Debug Read]
```

이 구조는 **데이터의 소유권**이다. 10개의 Manager를 새로 만들어야 한다는 뜻이 아니다. 적은 규모라면 한 파일 안의 순수 함수와 명시적인 단계 구분으로 충분하다.

### 2.3. 단일 소유권 계약

| 데이터 | 권위 소유자 | 허용 소비자 | 금지 |
|---|---|---|---|
| 함대 명령/대형 기준 | Fleet/Command state | 이동·표적 배정·UI | 무장 코드가 MOVE 목적지·슬롯을 덮어씀 |
| 함선 몸체 위치·회전 | Ship Body state | 무장·충돌·시각화 | 포탑이 별도 몸체 월드 Pose를 권위 데이터로 유지 |
| 무장 상대 회전·장전 | Weapon state | 사격·시각화 | FBX 렌더 노드를 장전/사격 권위 원본으로 사용 |
| 포구 월드 위치/방향 | 동일 틱 Body+Mount 합성에서 산출 | 발사체 생성 | 이전 렌더 프레임의 보간된 Transform을 판정에 사용 |
| 표적 후보 | 공통 Candidate Source | 함대/무장 | 무장마다 독립 전장 전체 재탐색을 기본 경로로 구현 |
| 명중·체력·격침 | Combat Simulation | UI·점수·전술 상태 | VFX 충돌/폭발 완료를 피해 근거로 사용 |

### 2.4. 탐색 단계 구분 [참조 아키텍처]

1. **BroadphaseCandidate:** 지리적으로 가능성 있는 객체. 탐지 성공이 아니다.
2. **DetectedContact:** 게임에 센서·시야 규칙이 있다면 그 규칙을 통과한 적. **센서 시스템은 현재 확정 기능이 아니므로 신설하지 않는다.** 초기에는 유효 적 후보 필터만으로 충분.
3. **AssignedTarget:** 함대/무장에 배정된 표적. 발사 가능한지는 아직 별개.
4. **FireEligible:** 실제 사거리·사격각·회전 상태·재장전·필요한 사선 검사를 통과.
5. **FireEvent / Hit / Damage:** 무장 발사와 투사체의 3D 교차로 발생하는 권위 사건.

`visible`, `targeted`, `hit` 같은 하나의 Boolean으로 이 과정을 뭉개지 않는다.

## 3. 강의 개념 매핑: 직접 구현/확장의 증거 계획

| 중요도 | 강의 원본(자료/페이지) | 강의에서 확인되는 개념 | FleetDoctrine 적용 | 직접 구현 증거 |
|---|---|---|---|---|
| **핵심 A** | **W08L1 pp.15–17** | 변환 합성 `TR ≠ RT`, 회전 중심 | Ship→Turret→Barrel→Muzzle 계층 변환 | 명시적 합성 계산, 독립 테스트, three.js 계산과 대조 |
| **핵심 B** | **W10L1 pp.36–39** | 경계 볼륨: Sphere/AABB/OBB, AABB 축별 비교 | 함선 피격 볼륨, 구역 판정 | 직접 작성한 포함/교차 함수와 경계 테스트 |
| **응용 확장 B+** | **W10L1 pp.23–26, 36–39** | 후보 축소, 광선 검사, 경계 볼륨 | **고속 포탄의 선분-볼륨 교차** | 이동 시작·끝을 검사하는 함수와 관통 누락 테스트. **세부 선분–AABB slab 해법은 본 설계의 응용 확장**으로 구분 |
| **기존 연결** | **W09L1 pp.24, 26, 31** | 모델/뷰/투영/뷰포트 변환, 직교·원근, 다중 뷰 | 현재 XZ→YZ 입력, 직교 미니맵·디버그 표시 | 현재 구현을 검증하고, 신규 확장 부분만 기여로 구분 |
| **조건부 최적화** | **W10L1 pp.23–27** | 전수 비교 비용, Uniform Grid, Spatial Hash, 셀 크기의 득실 | 적 후보·투사체 후보 공통 조회 | 직접 Cell 해싱 + brute force 일치/성능 비교 **실측 시에만** 채택 |
| **조건부 선택** | **W10L1 pp.33–38** | Octree/BVH와 경계 볼륨 | 복잡한 메시 충돌·컬링 후보 | 사용 시 출처·직접 기여 분리; 외부 `three-mesh-bvh`를 직접 구현으로 기재하지 않음 |
| **과제 필수** | **W11L1 pp.40–42** | 사용자 상호작용 ≥1, 강의 CG 기법 직접 구현·확장 ≥1, 문제 정의·증빙·제출물 | 플레이 가능한 2단계 수직 슬라이스와 기법 검증 | 수학 설명+테스트+Git diff+짧은 실제 시연 |

**출처와 응용의 경계:** 강의자료가 직접 설명한 원리(행렬 합성, AABB, 균일 격자 등)와 게임에 맞게 추가로 선택한 수치 알고리즘(선분–AABB slab, 이산 충돌 처리 순서, 포구 Pose 캐시)은 동일한 '강의에 적힌 공식'으로 주장하지 않는다. 확장 설계의 작성·검증 책임을 따로 남긴다.

## 4. 핵심 A: W08 계층적 3D 변환과 무장 조준

### 4.1. 월드 좌표계와 모델 좌표계

- **게임 공통 계약 [v2.2]:** 월드 +Y 위쪽, 게임 함선 로컬 +Z 전방. 함대의 회전과 함선의 독립 사격 자세를 구분한다.
- **FBX 예외:** Blender/FBX 모델 축, 스케일, 장착점 로컬 축은 모델마다 다를 수 있다. 이를 게임의 공통 +Z 전방 규칙과 **에셋 어댑터**로 연결한다.
- `rig-control.js`에 무장별 `yawAxis`, `pitchAxis`, 회전 부호/범위가 존재한다. **무조건 로컬 Yaw=Y축, Pitch=X축으로 가정하지 않는다.** 실제 자산별 피벗 계층과 합성 순서를 확인한다.

### 4.2. 합성 행렬의 의미

게임 규약을 열벡터/우측 행렬부터 적용으로 정하면 개념적으로:

```text
M_muzzleWorld = M_shipWorld
              · M_turretMountLocal
              · R_turretCurrent
              · M_barrelPivotLocal
              · R_barrelCurrent
              · M_muzzleOffsetLocal
```

- 변환 계층은 **실제 FBX 트리**의 부모–자식 경로에 따라 구성한다. 고정식 무장은 필요 없는 회전 노드를 생략한다.
- 점의 월드 변환은 `p_world = M_muzzleWorld · [p_local.x, p_local.y, p_local.z, 1]^T`.
- 방향 변환은 평행이동을 적용하지 않는 `w=0` 방향 벡터를 변환하고 정규화한다. 스케일·반사가 섞인 모델은 회전 성분을 분리하거나 직접 정의한 모델 어댑터 계약으로 처리한다.
- `T·R`과 `R·T`는 일반적으로 다르므로 포탑이 선체 원점을 도는 버그가 없는지 확인한다(W08L1 p.16).
- 임의 중심 `c`에서의 회전은 `T(c)·R·T(-c)`로 표현된다(W08L1 p.17). 피벗 기준 회전의 수학적 근거로 활용한다.

### 4.3. 직접 구현의 실용적 경계 [2단계 권장]

**직접 구현 추천:** 독립적인 작은 4×4 변환 합성/점·방향 적용 계산 또는 같은 수학을 명시한 참조 함수와 단위 테스트. three.js Scene Graph의 결과를 **비교 대상**으로 사용한다.

**재사용 추천:** 실제 렌더/애니메이션의 행렬 캐시, FBX 로딩, Quaternion 보간, 객체 트리 관리 등은 three.js 기능을 사용할 수 있다. 애플리케이션의 전체 행렬/카메라 엔진을 재작성할 필요는 없다.

사격 판정에 사용할 `MuzzlePose`는 **해당 고정 틱의 권위 Ship Pose + 현재 Mount 상태**로 산출한다. `renderer`가 보간한 프레임 상태를 역으로 읽어 명중을 결정하지 않는다.

```text
MuzzlePose {
  positionWorld: Vec3,
  forwardWorld: normalized Vec3,
  tick: integer,
  weaponId: stable ID
}
```

### 4.4. 사격각·조준

1. 월드의 표적 위치와 현재 포구 위치 차이로 방향 `d = normalize(target - muzzle)` 계산.
2. 표적 방향을 **해당 무장 장착 기준 좌표계**로 역변환한다.
3. 포탑/포신이 실제 피벗 축과 각도 제한 안에서 접근 가능한지 검사한다. 회전 속도 제한을 한 틱씩 적용.
4. 아직 목표 방향에 도달하지 않았다면 사격을 승인하지 않는다(정확한 허용 오차는 **[미결/설정]**).
5. 고정식 무장은 **실제 선체+장착 방향**의 허용 원뿔/각도 안에서만 발사한다. 표적 추적 때문에 함대 기준 방향을 돌리지 않는다.
6. 고정포의 +Z축 중심 선형 방향에서 **Roll만으로 전방 벡터는 변하지 않는다**. 다만 비축상 장착과 포탑 아크에는 Roll의 영향이 있을 수 있다(v2.2 §10.5).

표적의 미래 위치를 예측하는 탄도/리드 조준은 현 단계 **필수 아님**. 포탄 속도와 표적 운동으로 명중 가능성이 낮으면 다음 단계에서 실제 게임 규칙으로 검토한다.

### 4.5. 검증

- 선체를 월드 Y축으로 90° 회전했을 때 포구 위치와 `forwardWorld`가 함께 회전하는지 검증.
- 함선 위치만 바뀌면 포탑 로컬 각도는 그대로이고 포구 월드 위치가 동일 이동량만큼 바뀌는지 검증.
- 포탑 Yaw/포신 Pitch를 변경할 때 선체·함대 슬롯 좌표가 바뀌지 않는지 검증.
- 회전 제한 최솟값/최댓값, 장착 축 부호, 로컬 계층 회전 순서를 독립 테스트와 렌더 표시로 대조.
- 고정포가 뒤편 표적을 사격하지 않고, 같은 Y 좌표의 교전에서도 규칙상 Pitch/Roll을 일률적으로 봉쇄하지 않는지 검증.

## 5. 핵심 B: W10 경계 볼륨 및 3D 투사체 명중

### 5.1. 판정 볼륨의 역할 구분

| 볼륨 | 목적 | 비고 |
|---|---|---|
| `TargetingBounds` | 표적 후보 추출용, 충분히 보수적 | 대상 선택용; 실제 명중 확정 아님 |
| `HitBounds` | 탄체와의 실제 교차 검사 | 초기에는 Bounding Sphere 또는 단순 AABB |
| `AvoidanceBounds` | 함선 근접 회피와 겹침 완화 | 함대 이동 규칙과 연결, HitBounds와 같을 필요 없음 |
| `ScoreZone AABB` | 득점 구역 내부 대표점 검사 | **게임 규칙의 고정 9구역**, 공간 해시와 별개 |

수업 자료 W10L1 p.37은 Bounding Sphere, AABB, OBB의 정확도·비용 차이를 설명한다. **가장 복잡한 형상이 가장 좋은 초기 선택은 아니다.**

### 5.2. AABB 포함/겹침 [강의 원리]

점 `p`가 3D AABB에 포함되는 조건은 세 축 모두에서 `min_a <= p_a <= max_a`이다(경계 포함은 초기 권장; 이후 게임 정책 일관성 필요).

두 AABB `A`, `B`가 겹칠 필요충분조건은 세 축에서 모두 다음이 성립하는 것이다.

```text
A.min.x <= B.max.x && B.min.x <= A.max.x
A.min.y <= B.max.y && B.min.y <= A.max.y
A.min.z <= B.max.z && B.min.z <= A.max.z
```

W10L1 pp.37–39의 AABB 원리를 그대로 적용할 수 있다. **득점 구역 내부 검사에는 실제 함선의 대표 월드 위치**를 사용한다(v2.2 §21.4). 대형 슬롯이나 함대 앵커로 함선 수를 대신 계산하지 않는다.

### 5.3. 한 프레임 위치만 비교하면 발생하는 누락

투사체가 한 고정 틱 동안 `a = previousPosition`, `b = nextPosition`으로 이동할 때, `a`와 `b` 두 점이 모두 피격 볼륨 밖에 있어도 **선분 `[a,b]`는 볼륨을 통과**할 수 있다. 이를 단순 위치 검사로 놓치지 않게 설계한다.

**[2단계 권장]** 초기에는 **선분–구(sphere)** 또는 **선분–AABB** 교차를 직접 구현한다. 두 방법을 모두 직접 구현할 필요는 없다. 작은/빠른 탄체와 3D 입체 배치를 가장 단순하게 검증할 수 있는 쪽을 선택한다.

#### 선택 A: 선분–Bounding Sphere

```text
p(t) = a + t · (b-a),    0 <= t <= 1
|p(t) - center|^2 = R^2
```

- `R`은 **표적 구 반경 + 투사체 반경**(투사체를 구로 근사할 때).
- 구 방정식과 선분 매개식을 합성하여 이차방정식의 가장 이른 `t ∈ [0,1]`을 찾는다.
- 시작 위치가 구 내부라면 `t=0`을 일관되게 처리한다.
- `a=b`인 정지 투사체, 접선 접촉, 부동소수점 오차에 대한 예외가 필요하다.

#### 선택 B: 선분–AABB (Slab 알고리즘; **강의 내용의 응용 확장**)

`p(t)=a+t·d`, `d=b-a`, `0<=t<=1`에서 각 축이 상자의 `[min,max]` 구간 안에 있는 `t` 범위를 구해 **세 축의 공통 교집합**을 취한다.

```text
near = 0
far  = 1
for axis in [x,y,z]:
    if abs(d[axis]) < epsilon:
        if a[axis] outside [min[axis], max[axis]]: no hit
    else:
        t0 = (min[axis]-a[axis]) / d[axis]
        t1 = (max[axis]-a[axis]) / d[axis]
        sort(t0, t1)
        near = max(near, t0)
        far  = min(far, t1)
        if near > far: no hit
hit at t = near
```

- 투사체 반경이 있다면 AABB를 각 축으로 해당 반경만큼 확장한 뒤 선분을 검사하는 간단한 swept-sphere 근사를 사용할 수 있다(이 방식은 둥근 모서리를 정확히 표현하는 것은 아니므로 보수적 후보 검사로 해석).
- 함선이 회전하면 월드 AABB를 다시 계산하거나, 함선 로컬 좌표로 선분을 역변환해 고정된 로컬 AABB와 검사한다. **로컬 AABB 검사는 월드 관점에서 회전된 OBB에 대한 선분 검사**로 해석할 수 있다.
- 여러 함선과 교차했다면 **유효한 가장 작은 `t`**, 동점일 경우 **고정된 안정 ID**를 사용해 최초 타격을 결정한다.

**주의 — 움직이는 표적:** 위 알고리즘은 기본적으로 **하나의 고정 볼륨을 선분과 비교**한다. 한 틱 동안 크게 움직이거나 회전한 표적의 연속 충돌까지 자동으로 보장하지 않는다. 초기에는 작은 고정 틱, 보수적인 swept broadphase, 위치 상태 일치 테스트로 범위를 정하고, 완전한 연속 충돌 판정(translation/rotation CCD)은 **[후속 검토]**로 기록한다. 기능을 과장하여 '모든 상황의 관통 누락 0'이라고 주장하지 않는다.

### 5.4. 발사와 피격의 단일 소유권

- 포탄 위치·속도·발사 팀·소유자·수명·피해는 **Projectile 데이터**에서 관리한다.
- 포탄 생성은 동일 틱의 **MuzzlePose**로만 수행한다.
- 발사 VFX의 눈에 보이는 위치가 권위 포탄 위치가 아니다.
- 명중 결과가 확정되면 피해·격침을 **한 번만** 반영한다. 같은 투사체에 대한 중복 피해를 방지한다.
- Friendly Fire 허용 여부, 탄체 관통/폭발 범위 등은 **[미결]**. 새로운 게임 규칙으로 조용히 추가하지 않는다. 초기에는 충돌 대상 팀 필터를 설정으로 분리하고 적용한 가정을 명시한다.
- 3D 사선(occlusion/first hit) 검사는 실제 게임 기획의 차폐 조건과 연결할 수 있지만, 초기에는 충돌 판정의 올바른 **최초 명중**부터 확보한다.

### 5.5. 성공 증거

- `t` 위치에서 선분과 표적 볼륨이 교차하지만 두 끝점은 모두 밖인 사례가 실제로 명중함.
- 선분이 스치거나 평행하게 지나가고 상자 바깥에 남는 사례는 명중하지 않음.
- 한 줄에 두 표적이 있으면 가장 먼저 만나는 표적만 맞음(탄체 관통 규칙 미도입 시).
- 함선 선체가 Pitch/Yaw/Roll을 변경해도 명중 판정 볼륨이 올바르게 따라감.
- 타겟이 격침된 후 다시 후보·피격 대상으로 사용되지 않음.

## 6. 후속 CG 후보: W10 공통 공간 탐색과 Spatial Hash

### 6.1. 성능을 개선하기 전 책임을 먼저 통일

**[2단계 권장]** 현재 규모에서는 `CombatCandidateSource.query(params)` 같은 공통 질의 인터페이스만 만든다. 내부 구현은 **단순 전수 검사**여도 된다. 함대별·포탑별로 서로 다른 전역 탐색 로직을 복제하지 않는다.

```text
queryTargets({ team, center, radius, targetTypes, excludeIds })
    -> 후보 Ship ID 집합   // 탐지/발사 승인/명중 아님
```

범위, 팀, 종류가 무장마다 다르면 공유 결과를 잘못 잘라 유효 표적을 누락해서는 안 된다. 필요시 같은 조회 소스에 더 넓은 범위의 **명시적 별도 질의**를 허용한다. `GroupContact`는 불필요한 캐시가 될 수 있으므로 성능 문제가 확인되기 전까지 필수 구현이 아니다.

### 6.2. 3D Spatial Hash [후속 검토]

강의 W10L1 p.26의 2D `(floor(x/h), floor(y/h))` 개념을 3D로 확장:

```text
cell(p) = (floor((p.x-origin.x)/h),
           floor((p.y-origin.y)/h),
           floor((p.z-origin.z)/h))
```

- `h > 0`은 Spatial Hash **셀 크기**. 플레이어의 `COMMAND_GRID.spacing`, 함대의 **이동 격자 간격**, **9개 득점 구역**과 독립이다.
- 셀 키에 해당 객체 ID를 등록한다. 셀을 월드에 있는 수많은 개별 Mesh로 만들 필요는 없다.
- 질의 반경 `r`이 `h`보다 크거나 대상 크기가 큰 경우 **무조건 주변 26셀만 검사하면 후보를 누락할 수 있다**. `r/h`와 볼륨 크기를 고려해 방문 셀 범위를 계산한다.
- 큰 함선은 여러 셀에 등록하거나 경계·질의 범위를 보수적으로 확장하고 ID로 중복 제거한다.
- 움직임 이후에 재구축/증분 갱신 중 하나를 선택하고 질의가 참조한 위치 버전을 일치시킨다.
- Broadphase는 **거짓 양성은 허용하되 거짓 음성은 없어야 한다**는 정확도 원칙을 지킨다.

### 6.3. 의무 검증 조건

- 동일 배치·동일 탐색 조건에서 Spatial Hash 반환 후보가 **전수 검사 결과를 누락 없이 포함**하는지 검증한다.
- 원점 부근, 음수 좌표, 셀 경계, 이동 후 셀 전환, 큰 선체, 서로 다른 무장 사거리, 높은 Y 차이를 테스트한다.
- `N` 객체/`W` 무장 수·질의 수·후보 수·인덱스 재구축 비용·프레임 시간 평균/p95를 측정한다.
- 전수 탐색보다 느리거나 관리 비용이 큰 범위에서는 **기본 전수 검사 경로를 유지**한다.
- OverTheHorizon의 Job/Burst 병렬 구조를 모방하는 이유만으로 JS Worker나 별도 프레임워크를 만들지 않는다.

### 6.4. BVH와 Octree에 대한 판단

- 강의 W10L1 pp.33–38: **Octree**는 공간 자체를 분할하고, **BVH**는 객체·삼각형을 경계 볼륨으로 묶는다. 둘의 목적과 데이터 단위를 구분한다.
- `rigging-test/rig-safety.js`의 `MeshBVH` 사용은 기존 **라이브러리 적용**이며, 이를 직접 구현의 증거로 제출하지 않는다.
- 매우 정밀한 함선 메시 피격/리깅 충돌이 실제 필요해질 때 BVH를 별도로 고려한다. 초기 2단계는 단순 HitBounds로 충분할 가능성이 높다.

## 7. 2단계 시뮬레이션 실행 계약(권장)

### 7.1. 게임 논리와 렌더의 분리

```text
PREPARATION
  └─ 명령·편성 변경, 구매/배치(후속 단계), 시뮬레이션 시간 정지
RUNNING (고정 dt, 기존 프로토타입은 임시 1/60초)
  1. 이전 틱에서 확정된 명령/상태 읽기
  2. 유효 적 후보/단순 임시 TargetPlan 정하기
  3. 함대 기준점 및 개별 함선 이동·자세 확정
  4. 같은 틱 Body/Mount/Muzzle Pose 계산
  5. 무장별 할당 표적과 사거리·아크·쿨다운 검사
  6. 발사 이벤트 생성; 투사체 이동 구간/명중 판정
  7. 피해·격침·표적 무효화/이벤트 일괄 확정
  8. [후속 v2.2] 9개 구역 득점·현재 점수 승패 판정
  9. 전투 구간 시간 소진 시 PREPARATION으로 정지
RENDER (가변 FPS)
  └─ 게임 상태를 읽어 Mesh·이펙트·HUD·미니맵만 표시
```

`RUNNING` 단계 번호는 **권장 논리 순서**이다. 실제 신규 포탄을 발사 틱에서 즉시 한 번 움직일지, 다음 틱부터 움직일지는 **[미결]**로 지정하고 이중 적분/이중 명중이 없도록 테스트로 확정한다. 피격 이후 구역 득점을 계산하는 v2.2 규칙은 그대로 유지한다.

### 7.2. 상태 일관성

- 시뮬레이션이 참조한 각 대상의 위치·생존·팀은 동일하게 정의된 틱/스냅샷 시점에 기반해야 한다.
- 이동 후 포탄을 발사하면 사격에는 이동 후의 **최신 권위 Ship/Mount Pose**를 사용한다.
- 근거 없이 과거 틱의 공간 인덱스와 현재 위치를 섞어 유효 후보를 누락하지 않는다.
- 한 함선이 격침되면 신규 공격 이벤트를 생성하지 않고, 이후 ScoreZone에서도 살아 있는 함선으로 세지 않는다.
- 같은 시뮬레이션 틱에서 두 팀이 동시에 사건을 발생시킨다면 적용 순서를 재현 가능하게 정한다. 물리 엔진 전체의 비트 동일 결정론까지 약속하지 않는다.
- `PREPARATION` 동안 발사체/재장전/상태가 시간이 흐르거나 UI 갱신 때문에 달라지면 실패다.

### 7.3. UI와 CG 디버그 표시

기존 W09 카메라·직교 뷰를 **재사용**해 다음을 임시 토글로 표시하면 구현/과제 검증에 도움이 된다.

- 개별 포구 축, 무장 조준 방향 및 허용 사격 원뿔/각도
- 현재 할당한 표적 ID, 발사 가능/불가 이유
- 함선 `HitBounds`와 포탄의 지난 위치→현재 위치 선분
- 포탄의 최초 교차 지점·법선(계산한 경우)
- 함대 원래 경로·대형 슬롯, 명령 유지 사격 중 불변 상태
- 공간 해싱 도입 시 셀과 Broadphase 후보 수(성능/정확도 검사용)

새로운 **항상 표시되는 플레이어 조작 UI**를 요구하지 않는다. 디버그 정보는 선택적으로 표시하고 실제 게임의 조작은 간단하게 유지한다.

### 10.3. 범위 통제

- **수업과 게임의 목적이 일치하는 CG 구현 1~2개를 정확히 수행하는 것이 우선**이다.
- 게임 기능과 직접 관련 없는 Octree/BVH 전체 재구현, 범용 ECS, Netcode, 자체 물리 엔진, 모든 로컬 좌표 변환 함수의 전면 교체는 권장하지 않는다.
- 평가 보고서에는 최종 동작하는 기능만 '구현 완료'로 서술하고, 향후 확장 후보는 별도 표기한다.
