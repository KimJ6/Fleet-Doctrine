## 구현 현황 — 2026-11-23

`web/simulation.js`에 이동·사선 후보용 균일 셀과 포구 레이 최초 접촉, 아군 차폐, 동일 틱 피해 확정, 임시 즉시 피격 및 표시 분리를 적용했다. 셀 크기 8과 모델 경계 상자의 외접 구를 이용한 피격 반경은 임시값이다. 무장 포구 계층을 로드 시 로컬 변환 데이터로 캡처하고, 조준 후보와 포구의 위치·방향을 행렬로 계산한다. 함대 단위 적 후보를 공유하며 함선별 최대 4개 근사 후보에 무장을 배분한다. 적 최초 접촉이 없는 사격의 자기 구조 메시 검사를 생략한다.

경순01 FBX의 선체 회전 및 포탑·포신 자세를 포함한 포구 변환 24건에서 데이터 계산과 three.js 월드 위치·방향이 일치했다. 이전 공간 검색 시험에서는 100개 시드 고정 레이와 200척 전수 대조에서 사용 중인 구형 판정의 후보 누락이 없었다. 별도 소규모 시험으로 준비 정지·아군 차폐·정밀 검사 보류·피격·동시 격침을 확인했다. Edge의 소프트웨어 렌더 환경에서 전투를 25초 실행했을 때 오류 없이 게임 시간 약 15.6초가 진행되었다. 이는 실제 GPU 성능이나 기존 버전과의 비교 결과가 아니다.

함선별 무장 상태에 고유 ID·각도·재장전·표적 ID를 저장하고, 확정 공격 사건에 공격자·무장·수신 함선·시작/명중 위치·피해를 기록한다. 포구~명중점의 짧은 선은 사건과 연결된 표현이며 피해 권위가 아니다. 슬롯 템플릿은 함선 수나 간격이 바뀔 때만 재생성한다. 간단한 마지막 틱 후보/검사/발사 건수도 기록한다.

Edge 소프트웨어 렌더 환경에서 전체 16척을 25초 실행한 추가 확인에서는 게임 시간 약 19.17초가 진행되고 56개 공격 사건 및 체력 감소·격침이 발생했으며 페이지 오류는 없었다. 이 수치는 일회성 기능 관찰이며, 브라우저/시스템 부하와 장면이 다른 과거 결과와 성능 비교할 수 없다.

기존 회전 간섭 AABB 근사와 자기 구조의 메시 포구 검사는 남아 있다. 시뮬레이션과 리깅 객체의 완전 분리, 여러 함종의 피격 형상과 근사 오차, 실제 모델의 회전/사선 시각 검수, 동일 작업량·실제 GPU 성능 비교 및 나머지 수용 검증은 미완료다. 앞선 초기 배치와 같은 16척·6초 지표의 재측정과 비교 한계는 성능 기록에 남겼다.

## 2026-11-23 2단계 시제품 검증 마무리

**판정:** 사용자가 게임 플레이에서 일정한 형상 오차를 허용하고, 구형 피격 범위의 시각적 차이는 향후 실드로 대응할 계획임을 전제로, **현재 경순01 16척 시제품의 기능 검증을 마무리**한다. 아래 통과는 시제품에서 실행한 사례에 대한 판정이며, 문서의 모든 엄밀한 D2 조건·성능 목표·다른 함종을 통과했다는 의미는 아니다. 사용자가 체감 성능 개선을 확인했으나, 자동 환경의 동일 작업량·실제 GPU 전후 개선율은 검증하지 않았다.

- **명령/UI:** Edge 헤드리스에서 목적지 XZ→YZ 클릭 확정, 함선 드래그 순서 변경(4척 중 A-1/A-2), WASD 전진, 창 크기 변경, 시작·정지와 목적지 보존을 확인했다. 동일 실행에서 교전 중 발사까지는 확인하지 않았고, 다음 근거리 전투에서 이동 목적지 보존을 별도로 확인했다.
- **표적과 명령:** 아군 Z=18/적군 Z=-18의 16척 전투, 실제 대기 8.5초 관찰에서 게임 시간 약 6.97초, 공격 56건. 관찰 시 무장 표적 할당 80건의 고유 표적은 12척, 아군 표적은 0건이며 세 함대의 MOVE 목적지가 유지됐다. 한 장면의 배분 결과이지 모든 상황에서의 적정 분산·표적 생존 보장은 아니다.
- **회전 제한:** 위와 같은 근거리 배치의 별도 8초 관찰에서 회전 배치 호출 431회, 각도 변화 1,508건, 한 번의 최대 변화 7°, 설정 각도/속도 제한 위반 0건. 실제 가동 부품 메시의 모든 중간 경로에 대해 무관통을 인증한 것이 아니며, AABB 근사에 따른 시각 간섭은 사용자 허용 오차의 범위에서 플레이 중 추가 확인한다.
- **에셋 오류:** 분석 해시를 응답에서 의도적으로 불일치시킨 별도 실행에서 안전 상태 함선 0/16, 공격 0건, 사용자에게 사격 보류 안내가 표시됐다. 페이지 오류는 없었다.
- **저장 순서:** 검색 인덱스 등록을 역순으로 바꾼 동일 입력에서 후보 ID 순서가 같았고, 함대 배열 순서만 역순으로 바꾼 이동 90틱에서 함선 ID별 위치·속도가 같았다. 편성 내 함선 순서 변경은 슬롯 배치를 바꾸는 사용자 기능이므로 이 동일성 시험에 포함하지 않았다.

**후속으로 남기는 차이:** 실드 자체와 표시/피격 크기 일치는 미구현; 여러 함종과 실제 GPU는 추후 해당 자산·장비에서 검증; 화면 탄 1/10/100 비교는 다중 탄 표현이 구현되면 수행; 즉시 판정 외 시간 모델은 최종 기획 결정 시 비교한다. 포구 메시 검사의 과차단 가능성, 시각 간섭과 무효 입력 오류 표시는 플레이 테스트에서 문제가 확인되면 다룬다. 이러한 잔여 항목을 이미 구현·검증된 기능으로 표현하지 않는다.

## 1. 목적과 적용 우선순위

전투 처리의 기본 단위를 화면 객체가 아닌 **함선 상태, 무장 상태, 공간 후보, 공격 사건과 피격 결과**로 바꾼다. 피격 상태와 체력의 확정 책임은 피격 함선 측에 두며, 발사 시 포구 기준 레이를 사용한다. 여러 화면 탄이 보이더라도 탄마다 고유한 충돌 객체·매 틱 충돌 검사가 생기지 않도록 시각 효과와 규칙상 공격을 분리한다. 실제 독립 발사 사건과 후보가 늘면 연산이 늘 수 있으므로 **탄 수와 무관한 무조건적 O(1) 성능을 주장하지 않는다.**

사용자의 명시적인 기존 2단계 상세 설계 폐기에 따라 이 문서가 재설계 대상이다. 기존 4.2~4.3 및 단계 2 전문은 폐기본에 보존한다. 게임 규칙의 확정·권장·미결 및 원칙은 v2.2와 사용자 지시가 우선한다. 사례는 근거이지 구현 완료가 아니다. 현재 코드에는 공간 검색·즉시 판정 및 데이터 기반 포구 계산의 일부가 적용되어 있다. 기존 5Hz 갱신·AABB 회전 근사와 메시 포구 검사는 남아 있으며, 새 설계 전체가 구현된 것은 아니다.

**판정의 시간은 미결:** 본문은 구현·비교 가능한 **발사 틱 즉시 결과 확정**을 기본 시제품 가정 `HITSCAN_SNAPSHOT`으로 사용한다. 이는 실제 비행 중 이동·차폐를 보존하지 않는 규칙 변경 가능성이 있어 최종 게임 규칙으로 자동 채택하지 않는다. 실착탄 시간과 후속 가로막힘이 반드시 필요한 경우 6.6절 대안을 비교하고 상위 기획과 정합성을 확인한다. 정확도 절충 허용은 아군 사선·포탑 제한 전부를 삭제하라는 승인과 같지 않다.

## 2. 2단계 범위와 불변식

**포함:** 0~1단계의 기존 준비 UI·명령 격자·카메라·편성·MOVE, 대칭 유한 전장 및 9개 분리 3D 구역, 양측 동일 전투 규칙, 대표 리깅 함선, 근사 표적 배분, 포구별 사선과 함선 피격, 동시 피해·격침, 점수·목표 점수 승리, 준비/전투 반복. 별도로 점수 경제가 구현되기 전에는 전멸을 즉시 승리·재기 불능 패배로 판정하지 않는다.

**후속:** 구매·예비·증원과 양측 경제 AI는 3단계, PATROL과 추가 교전 정책은 단계 4~6. 유도/곡선/지속 빔과 다양한 함종의 완전 검수는 별도 범위다. 2단계의 제한을 전체 기획에서 기능을 삭제한 것으로 보지 않는다.

**불변식:**

1. 명령용 격자 교차점과 함선·자동 목표의 연속 3D 위치는 다르다. 점수 구역, 명령 격자, 내부 검색 셀은 별개다.
2. `MOVE + OPPORTUNISTIC_FIRE`는 공격을 위해 함대 목적지·경로·대형을 변경하지 않는다. 표적은 전역 최근접 정렬이나 강제 1:1/단일 집중이 아니다.
3. 고정포는 실제 선체·장착 방향만 사용하고 회전포는 모델별 축·각도·속도를 사용한다. 활성 교전에서 선체 Pitch/Roll을 일률 금지하지 않는다.
4. 준비 단계에서 고정 틱·피해·득점·재장전이 정지한다. 상태와 미완료 표현/공격을 선택한 시간 모델에 맞춰 보존하고 수정하지 않은 명령을 유지한다.
5. 함선/무장·포구 위치와 결과는 **시뮬레이션 데이터**가 권위다. 보간된 화면 노드나 효과 충돌이 피해를 결정하지 않는다.
6. 정상 접합 예외는 지정 부품 쌍·국소 영역에만 적용한다. 사용자가 정확도 절충을 허용했으므로 회전 중 시각 간섭은 성능과 함께 평가하되, 기계적 제한·사선 차단의 적용 범위와 알려진 누락을 숨기지 않는다.
7. 격침은 HP 확정 후 발생하며 기존 슬롯을 비운다. 한 틱의 동시 사격·득점 순서는 7절을 따른다. 사용자 명령에 숫자 입력을 요구하지 않는다.

## 3. 권위 데이터와 소유권

데이터 구조는 논리 계약이다. 초기에는 작은 JS 배열/typed array와 정수 ID를 사용할 수 있다. `TypedArray`, Worker, Wasm은 자동 성능 보장이 아니며 측정 후 선택한다. 축별 배열(SoA)과 묶음 레코드(AoS)는 계측에 따라 바꿀 수 있고 외부 소비자는 저장 레이아웃에 의존하지 않는다.

## 4. 공간 검색과 근접 완화

### 4.1 3D 셀과 AABB

초기 제안은 유한 전장을 덮는 **독립 3D 균일 셀 검색**이다. 셀 길이·원점은 명령 격자와 별도 설정이며, 16척에서는 전수 비교보다 느릴 수 있으므로 동일 시나리오에서 비교한다. 각 틱의 동일한 기준 자세로 `shipAabb` 또는 반경을 계산하고 **해당 경계가 닿는 모든 셀**에 shipId를 등록한다. 큰 함선과 경계 접촉·부동소수점 여유 때문에 중심 셀 하나만 등록해선 안 된다. 셀 외부/전장 경계를 명시적으로 처리한다.

`queryAabb(q)`는 q에 겹치는 셀의 ID를 모으고 중복 제거한다. AABB 후보는 실제 충돌·사거리·명중이 아니다. 좌표/크기 정규화, 경계 포함, 음수 셀 인덱스, 범위 검증은 공통 함수로 일원화한다. 검색 결과는 stable ID 순으로 처리하고, 파괴·이동 후 stale ID나 이전 틱의 셀을 사용하지 않는다. 증가분 갱신과 전체 재구축 중 어느 쪽이 적합한지는 밀집도·규모 측정 후 선택한다.

- **정확성 경계:** 근접 완화와 사선 차단의 후보는 필요한 쌍을 누락하지 않도록 보수적으로 찾는다. `QueryAABB`의 결과에 근접 거리·구/캡슐 등의 좁은 검사와 실제 차폐 판정을 적용한다.
- **근사 가능 경계:** 표적 탐색은 근접 셀부터 살펴 유효 후보가 있으면 더 먼 셀을 중단할 수 있다. 목표 탐색의 조기 종료를 근접·차폐 후보에 적용하지 않는다. 밀집 셀에서도 임의 고정 개수로 뒤의 차단 함선을 누락하지 않는다.
- **기준 구현:** 작은 N에서는 전수 검색을 참조 구현으로 유지한다. 같은 스냅샷에 공간 후보 결과를 비교하며, ID 중복 제거와 실제 유효 쌍 누락 0건을 확인한다. 규모·분포가 다르면 셀화가 더 느릴 수 있다.

### 4.2 근접과 슬롯

모든 함선의 틱 시작 위치를 읽어 개인별 근접 후보를 조회하고 대칭적인 거리 완화를 계산한다. 각 함선의 이동 결과는 별도로 저장해 읽기 순서에 따라 상대 위치가 바뀌지 않게 한다. 거리 비교는 제곱거리로 우선 거르고 실제 완화에 필요한 후보에만 길이를 구할 수 있다. 동일 위치의 분리 방향은 안정 ID로 결정한다. 큰 반경·경계·밀집 및 이동 중 충돌 회피의 정확도는 별도 검증하며 **완전 무충돌을 약속하지 않는다.**

함대 슬롯 ID와 사용자의 순서는 전투 중 고정하고 격침 슬롯을 빈 상태로 둔다. 대형 크기·순서·편성에 변동이 있을 때만 슬롯 템플릿을 재생성하고, 함대 자세의 현재 변환은 그 틱에 적용한다. 준비 중 명시적 편집만 편성을 변경하며 이동 중에는 순간이동하지 않는다.

## 5. 무장·조준·사선

### 5.1 표적 후보와 낮은 정확도

함대 또는 근접한 검색 범위의 **공유 적 후보**를 셀에서 찾는다. 시제품은 가까운 셀 순회 중 유효 후보를 발견하면 먼 셀 검색을 조기 종료할 수 있다. 같은 셀의 동률은 stable ID로 처리하고 기존 목표 유지/기대 피해 페널티를 사용해 전 무장이 무조건 같은 최근접 한 척만 선택하지 않도록 한다. 점수·반경·재평가 간격은 설정 가능한 임시값이며 게임 밸런스가 아니다.

후보는 확정 명중이 아니다. 함선·무장마다 소속, 생존, 사거리, 고정식 또는 회전식 장착 범위, 재장전과 현재 도달 각도를 검증한다. 검색 대상의 목표 위치는 실제 연속 좌표다. 무장이 목표를 못 잡으면 발사하지 않으며 MOVE의 기준점이나 목표를 임의로 바꾸지 않는다. 함종·함대의 후보 공유가 포위 등 이후 전술에 제약이 되지 않게 후보와 명령을 분리한다.

### 5.2 데이터 기반 포구 변환

로딩 때 FBX 계층의 검증된 무장 피벗·축·포구 기준 변환을 `ShipType/WeaponType`의 불변 데이터로 읽고 함종 인스턴스가 공유한다. 같은 틱의 `shipWorld × mountLocal × yaw × barrelLocal × pitch × muzzleLocal`을 실제 부모 계층 순서에 따라 합성한다. 고정포는 없는 회전 단계를 생략한다. 점은 평행 이동을 포함하고 방향은 포함하지 않으며 단위 방향으로 정규화한다. FBX 축·부호와 스케일은 모델 어댑터에서 보정한다.

표적 방향을 장착 좌표로 변환하고 제한·각속도를 적용해 현재 각도를 갱신한다. 실제 FBX 노드를 좌우 후보마다 임시 회전시켜 화면 노드에서 결과를 읽는 것은 새 권위 경로로 삼지 않는다. 조준 계산과 모델의 회전 시각화는 분리한다. 대표 모델에서 수학 계산과 three.js 월드 변환을 비교하고, 부호·축·포구 방향·좌우 동기화는 시각적으로도 확인한다.

### 5.3 회전 간섭의 정확도 수준

사용자가 회전 판정의 정확도 절충을 허용했다. 무장 기본 각도/속도와 고정포는 유지하고, 같은 함선의 회전 간섭은 다음 후보를 비교한다.

- **R0 참조:** 기존 메시 BVH·중간 자세 검사. 비용과 열린 메시·표본 한계를 기록한다.
- **R1 근사 후보:** 사전 검수한 단순 형상/기계적 범위, 또는 보수적인 소수 구간 검사를 사용한다. 정상 접합·외장 관통·가동 포탑끼리 간섭을 비교한다.
- **R2 시각 간섭 허용 후보:** 기본 각도만 적용하고 포탑끼리 일부 겹침을 허용할 수 있다. 이때 허용 정도와 플레이 영향은 별도 시각 평가한다.

현 시제품의 도착 AABB 0.65/0.20 휴리스틱은 **비교 대상이지 검증된 기본안이 아니다**. 중간 경로와 얇은 부품 누락이 가능하다. 회전 정확도 저하를 포구 차폐 또는 탄 피해 규칙의 자동 생략으로 확대하지 않는다. 결과 선택은 일치율·과차단/누락·실제 화면과 16척 이상 성능 비교 후 결정한다.

## 6. 포구 레이·공격 사건·피격 함선

### 6.1 사건 단위와 예산

시제품의 **규칙상 발사 단위는 포구별 발사 사건 1개**를 기준으로 한다. 두 포구가 독립적으로 막히거나 각각 피해를 주는 경우 자동 통합하지 않는다. 포구 내 표현용 탄알 수는 Fx 설정으로 정하며 규칙상 사건·레이 수를 늘리지 않는다. 발수·피해 보존과 차폐 시 표시를 검증한다. 여러 포구/연사의 묶음 처리는 별도의 비교 후보이며 현재 승인된 정확성이라고 가정하지 않는다.

실제 포구 발사 사건을 무한히 늘려도 비용이 일정하다고 주장하지 않는다. 비용은 무장 상태 갱신, **실제 사격 사건 수**, 각 레이가 통과하는 셀 수·밀집도 및 피격 후보 수에 의존한다. 렌더 탄 수만 늘릴 때 게임 판정 요청 수가 늘지 않아야 한다. 이벤트 용량 초과를 조용히 버리지 않고 확장 또는 명시적 오류/중단으로 처리하며, 안전 차폐 후보를 임의 개수로 잘라내지 않는다.

### 6.2 발사 후보에서 포구 레이

1. 틱 시작 생존 상태의 무장 중 재장전 완료·후보 존재·거리·허용 각도·실제 조준 오차를 통과한 것만 `ShotCandidate`를 생성한다. 아직 재장전이나 포구 효과를 소비하지 않는다.
2. 포구별 확정된 현재 포구 위치·+Z 방향을 얻고 길이는 무장 유효 사거리 안에서 계산한다. 포구 위치 내부 시작, 포탄 반경/빔 폭, 유한 단위 벡터를 검사한다. 무효·검사 불가 시 보류한다.
3. **자기 구조의 포구 출구**는 승인된 무장/에셋 설정의 검사 형상으로 확인한다. 실제 메시 BVH는 참조 검수 수단이며, 대표 형상 정확도·비용을 측정해 시제품용 형상을 정한다. 정상 접합 예외를 발사 경로 전체로 확대하지 않는다.
4. 레이의 경로에 해당하는 셀을 조회한다. 초기에는 레이 전체 구간을 공격 반경만큼 팽창한 swept AABB를 질의하고, 향후 DDA 등으로 바꿀 수 있다. 이는 넓은 영역에서 후보가 많을 수 있으나 **경로상 함선이 빠지지 않아야** 한다. 9개 득점 구역으로 대체하지 않는다.
5. 자기 구조/모든 살아 있는 함선의 첫 관련 접촉을 거리 `t∈[0,range]`로 비교한다. 아군을 표적 후보에서는 제외하더라도 **차폐 후보에서는 제외하지 않는다.** 최단 거리 오차 허용치와 동률 시 stable ID/차폐 우선순위는 설정하고 결정적으로 처리한다.

### 6.3 함선 중심 판정과 첫 차단 확정

단순히 함선별로 모든 공격을 순회하지 않는다. `ShotCandidate → spatial candidates → (attackId, shipId)` 관계를 생성하고 중복을 제거한 다음, **관련 함선의 피격 형상 데이터 기준으로만** 레이/확장 형상 교차를 일괄 계산한다. 한 쌍의 교차 결과는 후보 거리와 수신 shipId를 기록한다. 이때 함선이 자신의 피격 형상·피해 가능 여부를 제공하고 **함선 피해 확정기가 자신의 HP를 소유**한다.

공통 첫 차단 결산은 attackId별 후보 거리의 최소값을 결정한다. 이는 단일 발사가 두 함선에 중복 피해를 주지 않기 위한 순서 결정이며, 모든 공격을 전역 전수 비교한다는 뜻은 아니다. 같은 틱/사건에서 첫 차단이 자기 구조 또는 아군이면 **발사 보류**를 초기 정책 제안으로 둔다. 적이면 그 한 함선의 `HitCandidate`를 수신 목록에 전달한다. 첫 적 뒤의 아군은 해당 발사의 사전 보류 사유가 아니다. 더 가까운 다른 적은 실제 첫 대상이 된다.

발사 보류는 시각 탄·피해·재장전을 발생시키지 않는다. 유효 레이가 적과 만나지 않는 경우, 허공 발사 여부는 밸런스 미결이며 **시제품은 유효 적 첫 접촉이 있을 때만 발사**한다. 첫 차단을 찾는 비용과 함선별 기하 평가는 별도 계측한다. 완전 메시가 아닌 구/캡슐의 근사 사용은 에셋별 크기·과차단·누락을 표시한다. 레이 반경은 인접 판정을 고려하되 시각 크기와의 차이를 임시값으로 기록한다.

### 6.4 동시 피해와 표현

첫 적 접촉이 확정된 후보만 `AttackEvent`와 `ResolvedHit`을 남기고 해당 무장 재장전을 시작한다. AttackEvent는 해당 공격의 ID·포구·실제 3D 레이·진영·피해·틱을 스냅샷으로 갖는다. 같은 공격에 대해서는 `(attackId, receiverId)` 중복을 제거한다.

한 틱의 발사·차폐 판정은 같은 생존 스냅샷을 사용한다. 확정된 이벤트를 수신 shipId 기준으로 모아 합산하고 HP를 한 번 확정한다. 따라서 동일 틱에 상대를 격침시키는 양측의 발사는 모두 발생하는 **동시 처리 시제품 선택**이다. 피해와 사망 표시는 그 이후. 동률·이벤트 순서 및 피해 적용은 stable ID 순으로 재현한다. 사망 함선의 이펙트와 점수 집계는 실제 살아 있음 상태를 각각 읽는다.

FxEvent는 확정 공격과 피격을 읽는다. 시제품의 기본 표현은 **피해와 같은 틱에 종착점이 표시되는 짧은 탄/선형 효과**다. 시각 탄 1/10/100개는 동일 AttackEvent의 표시 선택이며 실제 발사·피해 건수를 늘리지 않는다. 명확히 보이는 느린 탄을 도입할 때는 실 피해 시간과 표시의 선후 관계를 6.6절과 함께 결정한다. 확정되지 않은 레이에는 명중 효과를 만들지 않는다. FX가 실패하거나 꺼져도 피해 결과는 변하지 않는다.

## 공통 공격 구간 판정과 후보 탐색 비교 설계 — 2026-11-25

- 상태: **재검토 설계 / 미구현·미측정**. 실탄·이동 빔과 지속 광선이 공통 공격 구간 판정기를 사용하도록 확장한다. A~D를 함께 구현해 동일 입력·판정·지표로 비교한다. 최종 운영 방식이나 성능 우위는 측정 전 확정하지 않는다.
- **2026-11-25 사용자 결정:** 실탄 `PROJECTILE`은 폐기한다. 무기 표현은 이동 빔 `BOLT`와 지속 광선 `RAY` 두 종류이며, 아래 과거 설계에서 실탄을 언급한 부분은 적용하지 않는다. 빔은 발사 시 한 번, 광선은 피해 주기마다 공통 공격 구간을 생성한다. 유형별 CSV 변경·구현은 아직 수행하지 않았다.
- 범위: 아래 A~D는 **피해 시점의 유한 공격 구간**에 대한 후보 생성·첫 차단 확정 비교다. 지속 광선은 피해 주기마다 구간을 만들고 실탄/이동 빔은 우선 발사 시 구간 하나를 만든다. 표현용 선·탄 수와 판정 사건은 분리한다. 이전 [대규모 전투 사례](../investigations/issue-001-large-scale-combat-cases.md), [기존 성능 조사](../investigations/issue-001-combat-performance.md)의 관측 환경·한계를 보존한다. 기존 `combatTick`의 레이별 AABB 조회는 A의 출발점이며, 현재 코드가 함선 주도 판정인 것은 아니다.
- 선수행: CSV 데이터 연결은 LC01만 부분 구현이다. CSV의 포 유형·유효 함선 상태는 구현 시 다시 확인하고 미확정 설정을 자동 보완하지 않는다. 비교용 합성 데이터는 CSV 사용자 값을 변경하지 않고 명시적 테스트 입력으로 전달한다. 실탄/이동 빔과 지속 광선의 실제 규칙·입력 분포는 각각 분리해 측정한다.

### R0. 공통 공격 구간으로의 재검토 및 우선 적용 규칙

**이 절이 아래 R1~R10의 지속 광선 전용 표현을 보완·대체한다.** R1~R10의 `ray/광선`은 별도 언급이 없으면 판정 시점의 **공격 구간 사건**을 뜻한다. 알고리즘의 입력은 공격의 화면 종류가 아니라 `(eventId, tick, owner, team, origin, end, radius, damage, safetyPolicy)`다. `eventId=(ownerShipId,weaponId,muzzleId,activationSerial,pulseIndex)`이며 같은 포탑의 여러 포구와 지속 광선의 서로 다른 피해 시점을 구분한다. 생존 함선 스냅샷은 공격 종류와 무관하게 공통이다.

| 무기 표현 | 초기 시제품의 사건 생성 | 중요한 판정 의미 |
|---|---|---|
| 실탄 `PROJECTILE` | 유효한 발사 포구마다 발사 틱에 포구→유효 끝점 구간 1개 | 그 틱에 결과·피해 확정. 화면 탄이 날아가는 동안의 표적 이동·차폐 변화는 반영하지 않는다. |
| 이동 빔 `BOLT` | 실탄과 동일하게 발사 틱에 구간 1개 | 길쭉한 투사체는 시각 표현이며 발사 후의 이동·충돌 물리 객체가 아니다. |
| 지속 광선 `RAY` | 포구별 조사 상태를 보유하고 `0, interval, ... < duration` 틱마다 **현재 확정 포구 자세**에서 구간 1개 | 각 피해 틱의 첫 차단·피격 결과를 새로 계산한다. 화면은 조사 중 연속 표현한다. |

모든 종류의 공통 파이프라인은 `구간 사건 생성 → A/B/C/D 후보 생성 → 수신 함선의 구 교차 검사 → 사건별 첫 차단 확정 → 함선별 동시 피해 합산 → 실드/HP → 결과·표현 사건`이다. B/C는 수신 함선이 후보를 조회하거나 함선별로 교차를 검사한다. A/D는 공격 구간이 후보 탐색을 주도하며, 공통 피해 결산의 수신자 소유와 후보 탐색의 주체를 혼동하지 않는다. `Projectile`이라는 이름의 이동 객체를 광선의 펄스마다 만들지 않는다. 표시 객체와 실제 사건 수는 별개다.

**발사·차단 계약:** 초기 공통 비교에서는 발사 조건(조준·재장전·실제 포구 등)을 만족한 뒤, 자기 구조 검사와 첫 함선 차단을 각 포구 사건에 한 번 수행한다. 시작 시 자기 구조 또는 첫 아군에 막힌 포구는 시작하지 않으며, 같은 포탑에서 하나 이상 시작되면 포탑 공유 재사용을 소비한다. 시작이 허용된 광선은 이후 피해 시점에 아군 또는 자기 구조가 막으면 해당 시점 피해만 보류하고 남은 조사를 유지한다. 적이 없는 빈 공간에 대한 발사 가능 여부는 기존 `combatTick`이 **첫 함선이 없을 때 발사를 확정하지 않는 점**과 차이가 있다. 일단 기존 동작에 맞춰 첫 적 접촉이 있는 포구만 발사 성공으로 보는 안을 비교 기준으로 두고, 빈 공간 발사·조사 여부는 별도 게임 규칙 결정 전까지 자동 변경하지 않는다. R1의 빈 공간 발사 허용 문장은 이 임시 기준에 의해 유보한다.

`origin`·`end`는 공격 생성기가 실제 조준 방향과 유형별 사거리로 정하며 A~D에 동일하게 전달한다. 현재 코드는 표적 중심까지의 `range`를 사건 길이로 쓰므로 곧바로 전체 무기 사거리까지 확장하면 표적 뒤 함선에도 맞을 수 있다. 초기 호환 비교는 **기존 유한 구간 길이**를 사용하고, 완전 사거리 구간으로 변경할지는 게임 규칙/별도 회귀에서 결정한다. 세 방식은 다른 판정 길이·시점으로부터 생긴 결과 차이를 탐색 방식의 정확도 차이로 합치지 않는다.

**광선 재사용:** 포탑에서 하나 이상의 포구가 조사 시작에 성공하면 시작 틱에 공유 재사용을 소비한다. 초기안은 `cooldownTicks >= durationTicks`; 조사 중 추가 발사 없음. 이미 활성화된 포구별 독립 사건은 같은 시작 상태와 종료 틱을 공유하되 이후 각자 차폐·피격된다. 발사 시작 실패와 조사 중 보류를 구분한다. 사건은 피해 시점에 실제 틱에만 생성하며, 종료 틱 제외, 준비/정지 중 시간 보존, 소유 함선 격침 후 다음 틱 중단을 따른다.

**피해 값:** `damage_per_round`는 빔과 광선이 공통으로 쓰는 포구별 발사 사건 1회의 피해다. 광선은 `ray_duration_sec` 동안 `ray_interval_sec` 간격으로 발사 사건을 반복한다. `damage_per_tick`은 사용하지 않는다. 지속·간격을 고정 틱 정수로 검증하고, 현재 런타임은 이 광선 열을 아직 읽지 않으므로 [CSV 개정·이관 계약](implementation-plan.md#phase-6-5-balance-data)을 따른다. 값은 사용자 입력 전 공란이다.

**실제 이동 충돌은 별도 모드:** 나중에 `previousPosition→currentPosition`을 공통 구간 판정기에 공급할 수 있지만, 그때는 투사체별 실제 위치·속도·수명과 해당 틱의 표적 이동을 함께 다뤄야 한다. 끝점의 함선 구만 검사하면 움직인 함선과의 상대적 스윕을 놓칠 수 있으므로, 정적 스냅샷 비교와 별도의 시간 구간·상대 운동·차폐 규칙과 참조 테스트가 필요하다. 이 가능성은 현재 즉시 판정의 구현이나 검증을 뜻하지 않는다.

**측정 확장:** 기존 [기록 CSV](../investigations/sustained-ray-benchmark.csv)의 `ray_*` 열은 스키마 1의 호환 이름으로 유지하되 공통 공격 구간 사건을 기록한다. `scenario_id`, `run_mode`, `notes`, `input_hash`에 공격 유형·즉시/주기·구간 생성·손상 사건 수를 명시하고, `ray_duration_ticks`/`ray_interval_ticks`는 RAY에서만 사용한다. 즉시 사건은 두 칸을 공란으로 남기며 0으로 표기하지 않는다. 공통 구간 인덱스·후보·판정 열은 모든 유형에 같은 정의를 적용한다. 동일 입력으로 A~D를 비교하고, 실탄 단발·이동 빔 단발·지속 광선·동시 혼합 공격을 별도 시리즈로 둔다. 서로 다른 무기·발사 수의 실행을 같은 작업량의 성능비로 계산하지 않는다. CSV 헤더를 임의 변경하거나 결과 행을 미리 만들지 않는다.

### R1. 모든 후보가 공유하는 게임 계약

| 항목 | 비교 시 고정할 의미 |
|---|---|
| 권위 상태 | `RUNNING`의 60Hz 고정 틱에서 이동·포탑 자세가 확정된 뒤, 살아 있는 함선과 포구의 동일한 불변 스냅샷을 사용한다. 이전 상태나 렌더 보간을 읽지 않는다. |
| 사건 단위 | 한 포탑의 포구별 지속 광선. 표시용 선 분할 수는 공격 수가 아니다. 같은 포탑의 포구들은 재사용 시간을 공유하고 각 포구의 사선·피해는 별개다. |
| 조사·피해 시각 | 시작 틱을 포함하고 종료 틱은 제외한다. `durationTicks`와 `intervalTicks`는 1 이상의 정수 고정 틱이다. 시작 후 `0, intervalTicks, ... < durationTicks`에서만 판정한다. 초기 비교값은 2초=120틱, 0.25초=15틱이며 한 포구의 최대 피해 횟수는 8회다. 이미 활성 광선도 준비/일시정지에서 진행하지 않는다. |
| 재사용 | 정상 발사 개시 시 포탑 공유 재사용을 시작한다. `cooldownTicks >= durationTicks`인 초기 비교 설정만 허용한다. 시작 틱에는 공통 자기 구조 검사와 선택한 후보 방식의 첫 차단 판정을 **한 번** 수행한다. 기존 호환 기준에서는 적을 첫 접촉으로 찾고 자기 구조에 막히지 않은 포구가 하나라도 있을 때 포탑 재사용을 소비한다. 빈 공간에 대한 발사 허용은 R0에 따라 별도 결정한다. 시작 틱의 동일 결과로 첫 피해 여부도 결정해 중복 계산하지 않는다. 시작에 실패한 포구가 조사 도중 늦게 새로 켜지지 않는다. 활성화된 포구가 이후 일시 차폐되면 남은 지속 시간 동안 조사 상태를 유지하고 피해 시각마다 재판정한다. |
| 레이·형상 | 포구별 현재 확정 출발점 `O`, 단위 방향 `D`, 사거리 `L`, 반경 `beamRadius`로 유한 구간을 사용한다. 초기 비교는 현재 구형 피격 범위와 `segmentSphere(O,O+D*L,center,shipRadius+beamRadius)`를 공통 정밀 판정으로 사용한다. 발사 함선은 일반 함선 교차에서 제외하지만 포구의 자기 구조 차폐는 별도로 검사한다. |
| 첫 차단 | 같은 광선의 교차값 `t` 최소인 생존 함선 하나를 선택한다. 양 진영 모두 후보에 포함한다. `abs(t1-t2)<=1e-9`면 안정 함선 ID 사전순으로 결정한다. 첫 대상이 아군이면 모든 함선 피해 0, 적이면 포구당 `damage_per_round` 피해다. 부유 소수 동률·경계 비교 기준을 모든 알고리즘에 동일하게 적용한다. |
| 자기 구조 | 포구 시작·변환·자기 차폐는 피해 판단에 앞서 공통 검사한다. 비용이 크면 기존과 같은 광선별 조건부 지연 검사도 별도 버전으로 비교할 수 있지만, 기본 비교 4개는 호출 시점과 결과를 일치시킨다. 차단·검사 오류는 사격 피해 불가로 처리하고 누락하지 않는다. |
| 이동·조준 | 광선 조사 중에도 실제 포탑 회전 제한·속도를 사용해 현재 방향으로 조사한다. 매 피해 시각에 현재 방향을 다시 사용하며 적이 벗어나면 빗나간다. 표적 잠금 자체가 적중을 보장하지 않는다. 조사 중 포탑의 새 표적 전환은 초기 비교에서 금지한다. |
| 피해 순서 | 모든 광선은 피해 적용 전 동일 생존 스냅샷을 읽는다. 4개 알고리즘 모두 동일 포구별 첫 결과를 만든 뒤 대상 함선 ID로 피해를 합산하고, 실드를 먼저 차감한 후 HP·격침을 확정한다. 표시 효과 실패가 판정에 영향을 주지 않는다. |
| 종료 | 지속 시간 종료, 소유 함선 격침 또는 유효 포구 제거 시 종료한다. 경로 밖으로 표적이 벗어나거나 아군이 가로막으면 그 피해 시각만 미적중이고 조사 지속 시간은 유지한다. |

초기 비용 분석 시 `B`=해당 틱에 피해 판정하는 활성 포구 수, `S`=생존 함선 수, `C`=방문·등록한 셀 수, `P`=중복 제거 후 광선–함선 후보 쌍 수로 기록한다. 고정 틱 시간, 5Hz 무장 조준, 광선 피해 주기와 렌더 프레임은 서로 다른 주기다. 포탑 다수의 실제 발사 시작이 한 틱에 몰리면 해당 틱의 부하가 발생하며, 벤치마크 목적만으로 발사·피해 시각을 이동하지 않는다.

### R2. 공통 데이터·파이프라인 및 전수 참조

`ActiveRay`는 안정 ID `(ownerShipId,weaponId,muzzleId,activationSerial)`, 진영, 시작/종료 틱, 다음 피해 틱, 발사 유형의 불변 피해·주기·사거리·폭 참조를 보유한다. 포탑당 `READY / ACTIVE / COOLDOWN`과 남은 재사용 틱은 별도다. 각 포구가 시작에 성공했는지는 포탑 안의 포구별 활성 비트로 기록한다. 기존 `shotEffects`는 지속 광선의 피해 상태를 소유하지 않는다.

매 틱의 `DueRaySnapshot`은 피해 시각이 된 광선의 `rayId, Oxyz, Dxyz, L, radius, owner, team, damage`를 담는다. `ShipSnapshot`은 `shipId, team, center, radius, alive, shield, hp`의 확정 배열이다. 기존 `ShipSpatialIndex`는 이동 후의 같은 함선 스냅샷에서 1회 구축하고 A/C/D가 공유한다. 광선 후보 인덱스가 필요한 B/C는 동일한 피해 시점의 광선들만 별도 구축한다. 틱마다 실제 데이터 레이아웃을 통째로 복제하는 비용과 인덱스 구축을 측정 범위에 포함한다. SoA·typed array는 비교군 전체에 같은 방식으로 적용하고 사용 여부에 따른 성능 이득을 사전에 주장하지 않는다.

`candidate(rayIndex,shipIndex)`에 대한 공통 정밀 검사는 유효 수치, 소유자 제외, `segmentSphere` 교차를 반환한다. 결과의 `first[rayIndex]`는 최소 `(t,shipStableId)`로 결산한다. `damage`는 첫 적 함선별 합산 버퍼로 전달한다. A/B/C는 완전 후보를 대상으로 이 공통 검사를 호출한다. D는 방문 순서에 의한 안전한 조기 종료를 허용하므로 실제 검사 후보 수는 달라도 최종 첫 결과·피해는 같아야 한다.

작은 입력의 별도 **전수 참조 E**는 각 유효 광선과 모든 생존 함선의 쌍을 정확히 한 번 검사하고 같은 최소·자기 차폐·동시 피해 규칙을 적용한다. E는 성능 후보가 아니라 정답 오라클이며, A가 같은 셀 누락을 갖는 경우를 방지한다. A~D는 E와 `rayId→차단 유형·shipId·t`, 포구별 피해 횟수, 함선별 실드/HP/생존 및 재사용·이벤트를 틱마다 비교한다. 경계 오차는 사전 지정 공차와 동률 규칙을 사용한다.

### R3. 공통 공간 규약과 누락 방지

- 셀 크기 h는 모든 후보에서 동일한 `ShipSpatialIndex` 설정으로 시작하고, h 변경 실험은 별도 시리즈다. 좌표→셀은 `floor(x/h)` 등 3축 각각 적용한다. 음수 경계·셀 모서리·수직 레이·0 방향 성분을 정의한다.
- 함선은 **구 전체의 AABB에 걸친 모든 셀**에 등록한다. 유한 반경 광선은 3D DDA의 중심선 셀만으로 충분하지 않으므로, 광선 반경으로 확장한 유한 선분의 셀 집합을 보수적으로 포함한다. 중심선 DDA와 주변 셀 확장을 사용한다면 `ceil(beamRadius/h)`와 경계 접촉·동률을 고려한 여유 셀을 포함하고 누락이 없음을 전수 참조로 검증한다. 동일 거리에서 셀 면·모서리·꼭짓점을 동시에 통과하는 경우 모든 관련 셀을 검사한다. 반경 0이라도 경계 접촉을 놓치지 않는 supercover 규칙을 사용한다.
- `L<=0`, 음수/비유한 반경, 비유한 좌표, 영벡터/단위 길이 오차는 피해 없이 오류로 기록한다. 광선 시작점이 함선 구 내부이면 `t=0`. 고정 틱마다 셀 재등록·함선 인덱스 재구축의 포함 범위는 후보별 기록한다.
- 같은 `(rayId,shipId)`가 여러 셀에 나오면 해당 틱의 방문 세대 표시로 중복 제거한다. 버퍼가 부족하면 용량 확장 또는 명시적 실패를 사용한다. 후보를 임의 상한에서 자르거나 프레임 여유에 따라 피해 사건을 누락하지 않는다.

### R3.1 후보 탐색 시간·공간 복잡도 검토

아래는 측정 결과가 아닌 한 피해 틱의 자료구조 연산량이다. `S`: 생존 함선 수, `B`: 해당 틱에 발생한 공격 구간 수(빔 발사와 광선 피해 펄스 합), `I`: 함선의 셀 등록 엔트리 합(다중 셀 등록 포함), `Q_A`: AABB 질의 셀 방문 수 합, `Q`: 반경 확장 DDA 셀 방문/등록 수 합, `H`: 셀 목록에서 읽은 원시 광선–함선 후보 엔트리 합(중복 포함), `P`: 중복 제거 후 후보 쌍 수. 해시 조회·삽입의 기대 O(1), 구 교차 1회 O(1)을 가정한다. `P<=B*S`, `H>=P`이나 여러 셀 중복으로 H는 B*S보다 클 수 있다. 데이터 구조 전체 스냅샷·함선 셀 구축 비용 O(S+I)와 공격 사건 O(B)는 각 행에 포함하며, 무장 조준·자기 메시 검사·렌더링은 별도다.

| 방식 | 예상 시간(한 틱) | 추가 공간·주의 |
|---|---|---|
| A0 현행 | 기대 `O(S+I+B+Q_A+H+Σ k_b log k_b)` | `O(S+I+B+max k_b)` 정도. `k_b`는 사건별 중복 제거 후 후보 수. 현 `query()`가 각 결과를 정렬하므로 정렬을 생략하지 않는다. |
| A1 정규화 | 기대 `O(S+I+B+Q_A+H+P)` | O(S+I+B+P) 상한. 전역 쌍 버퍼를 쓰지 않고 사건별 재사용하면 줄일 수 있다. 정렬 없이 최소 결과를 결정적으로 선택하는 조건이다. |
| B 함선별 광선 조회 | 기대 `O(S+I+B+Q+H+P)` | `O(S+I+B+Q+P)` 상한. 광선 셀 버킷·중복 제거 저장 비용 포함. 구현이 P개의 쌍을 정렬하면 추가 O(P log P). |
| C 점유 셀 일괄 결합 | 기대 `O(S+I+B+Q+H+P)` | `O(S+I+B+Q+P)` 상한. 함선별 후보를 정렬하면 추가 O(P log P). 공통 셀 탐색의 실제 구현 비용과 광선/함선 셀 교차 곱이 H에 포함돼야 한다. |
| D 광선별 DDA | 기대 `O(S+I+B+Q+H+P)` | 광선 셀 순회·중복 검사 버퍼를 재사용하면 O(S+I+B+S) 수준도 가능하나, 광선별 결과·후보를 보관하면 O(S+I+B+P). 안전한 조기 종료는 평균 Q/H를 줄일 수 있어도 동일한 최악 상한을 보장한다. |
| E 전수 참조 | `O(B*S)` 검사 + 스냅샷 `O(B+S)` | O(B+S)로 사건별 최소 결과를 누적 가능. 정확성 기준이며 일반적으로 운영 후보가 아니다. |

구간 길이 L과 셀 크기 h에 대해 **무기 폭·함선 반경이 h 대비 일정하게 제한**되고 축별 성분이 모두 비슷한 긴 대각선일 때, 한 구간의 AABB 방문은 대략 `O((1+L/h)^3)`, 중심선 DDA는 `O(1+L/h)` 셀이다. 이는 빈 공간의 셀 수 비교이지 전체 실행 시간이나 항상 성립하는 우위가 아니다. 축 정렬 광선의 AABB는 대체로 선형이며, 구간 반경 증가·supercover 주변 셀·셀 경계 처리에 따라 DDA 확장 계수도 증가한다. 큰 함선은 I와 중복 H를 증가시킨다. 비어 있거나 조밀한 공간, 배열/해시·정렬·할당과 실제 JS 엔진의 상수 시간에 따라 승자는 달라질 수 있다.

한 셀에 함선 S개와 구간 B개가 모두 들어오면 B/C/D의 유효 후보 P는 최악 `B*S`, 광선 인덱스를 구축하는 B/C는 여기에 Q와 중복 H가 더해진다. 공간 해시의 O(1)은 기대값이며 해시 병목·재할당의 최악 시간을 보장하지 않는다. 지속 광선의 초당 사건 수는 활성 포구 수/피해 주기이고 빔은 실제 발사 수에 비례한다. **연출용** 빔/선의 개수는 판정 복잡도를 결정하지 않는다. 광선 피격 샘플 사이의 일시적 교차 누락, 실제로 이동하는 투사체와의 시간 의미 차이는 그대로다. A0/A1/B/C/D를 동일한 사건 입력으로 측정해 비용을 비교해야 한다.

### R4. A — 기존 광선별 AABB 조회 (기준)

1. 기존 `ShipSpatialIndex.segment(O,end,beamRadius)`처럼 선분 양 끝의 축별 최솟값/최댓값에 광선 반경을 더한 AABB의 모든 셀을 순회한다.
2. 셀에 등록된 함선 ID를 수집·중복 제거한다. 해당 시점의 동일 생존 스냅샷을 읽고 아군을 후보에서 제외하지 않는다.
3. 공통 `segmentSphere`를 각 후보에 적용하고 광선별 최소 t를 결산한다. 현재 구현의 함수/Map·정렬 비용을 우선 유지한 **현행 기준 A0**을 측정한다.
4. 자료 구조의 차이와 AABB 자체의 비용을 분리할 수 있도록, B~D와 동일한 데이터 버퍼·중복 제거 방식을 쓰는 **정규화 A1**도 측정한다. A0/A1은 같은 결과여야 한다.

대략 비용은 광선별 AABB 셀 방문과 해당 셀의 누적 후보에 비례한다. 장거리 대각선은 AABB 부피가 커질 수 있다. A1은 비교 공정성용이며 성능이 A0보다 무조건 좋다는 뜻은 아니다.

### R5. B — 함선별 활성 광선 조회

1. 피해 시각이 된 각 광선의 반경 확장 선분이 지나는 셀을 R3의 보수적 DDA로 구하고 그 셀의 `beamBucket`에 광선 ID를 등록한다. 선분 전체 AABB 셀 등록 B0도 보조 기준으로 선택할 수 있으나 기본 B는 DDA 등록이다.
2. 각 생존 함선은 자기 구 AABB가 점유하는 모든 셀의 `beamBucket`을 읽는다. 광선–함선 중복을 제거하고 해당 함선의 구에 대한 공통 정밀 검사를 수행한다. 본인 광선은 제외하고 아군 차폐 광선은 포함한다.
3. 교차한 `(rayId,shipId,t)`를 광선별 최소 결과에 반영한다. 후보 순서가 달라도 동률 규칙으로 같은 결과를 만든다. 모든 함선의 후보 검사가 끝난 뒤 첫 차단과 피해를 확정한다.
4. 각 피해 틱의 광선 버킷을 비우거나 세대 번호로 재사용한다. 모든 활성 광선이 아닌 **해당 틱에 판정할 광선만** 등록한다. 매 프레임 광선 갱신·항상 모든 함선 순회 비용과 메모리는 별도로 기록한다.

함선이 후보를 찾아 교차를 검사한다는 사용자 요구에 가장 직접적으로 대응한다. 반면 B개의 장거리 광선 셀 등록과 S개의 함선 셀 조회가 추가되며, S가 크고 B가 작거나 광선이 자주 방향을 바꾸면 비효율적일 수 있다. 이전 결과의 후보를 캐시해 새 차단 가능성을 무시하지 않는다.

### R6. C — 점유 셀 기준 일괄 결합

1. R3과 같은 함선 셀 버킷과 B와 같은 `beamBucket`을 구축한다. `beamBucket`이 존재하고 함선도 등록된 **공통 점유 셀만** 조회한다.
2. 각 공통 셀의 함선 목록×광선 목록을 후보로 만들되, `(rayId,shipId)` 방문 세대로 중복 제거한다. 후보의 자가 함선은 즉시 제외한다. 함선별 임시 버킷에 광선 ID를 모으거나 광선별 최소 결과를 누적할 수 있으나, 두 자료 구조를 섞어 B/C의 비용을 숨기지 않는다.
3. 모은 후보를 함선 ID 순으로 일괄 처리하여 해당 함선의 구와 광선의 공통 정밀 검사를 수행한다. 각 광선의 최소 t·동률 ID를 갱신한 뒤 공통 피해 확정으로 넘긴다. 후보 검사 순서는 정확한 첫 충돌을 대신하지 않는다.
4. 공통 셀 탐색·교차 곱·중복 제거·함선별 버킷 작성·정밀 검사·최소값 결산을 별도 계측한다. B와 동일한 광선 셀 등록을 쓰므로 **순수 B 대 C의 차이는 함선 쿼리 대 공통 점유 셀 결합**이다.

성긴 장면에서 양쪽이 존재하는 셀만 처리하는 이점이 있을 수 있다. 반대로 한 셀에 광선과 함선이 집중되면 곱셈 후보가 폭증하고 수집·재정렬 비용이 생길 수 있다. C는 피해 검사 주체가 함선인 설계 후보이며 B보다 저렴하다고 미리 단정하지 않는다.

### R7. D — 광선별 함선 셀 순회 및 첫 차단 조기 종료

1. 피해 시각 광선마다 R3의 반경 확장 supercover DDA로 선분을 **포구에서 먼 방향 순서**로 순회한다. 함선 셀 버킷을 조회하고 중복 함선은 한 번만 공통 `segmentSphere`로 검사한다.
2. 교차 시 기존 `bestT`를 갱신한다. 아직 방문하지 않은 셀의 **보수적인 최초 진입 거리 하한**이 `bestT`보다 확실히 클 때에만 순회를 종료한다. 광선 반경 주변 셀과 함선이 다중 셀에 걸치는 경우를 포함해야 하며, 동률 가능성이 남으면 관련 셀을 계속 검사한다.
3. 초기 구현에서 이 하한의 보수성을 증명하거나 E의 경계 시험을 통과하지 못하면 조기 종료를 끄고 끝까지 순회한다. 빠르기 위해 차단 함선을 생략하지 않는다. `D-noearly`와 `D-early`의 첫 결과를 비교해 조기 종료의 기여를 따로 표시한다.
4. 첫 차단을 찾은 이후 공통 자기 구조 검사·피해 결산을 적용한다. D는 광선이 후보 탐색을 주도하므로 엄격한 함선 주도 후보 검색안이 아니다. 피해 확정·실드/HP는 함선 데이터가 소유한다는 점을 결과표에 분명히 기재한다.

차단물이 가까우면 조기 종료가 유리할 가능성이 있다. 반면 빈 공간, 모든 광선이 장거리, 큰 광선 반경, 셀의 반복 함선이 많으면 순회·중복 검사 비용이 남는다. 결과가 유사한 경우 B/C 대비 판정 주체와 비용의 절충을 사용자가 평가할 수 있게 한다.

### R9. 공정한 성능 비교 절차

**두 가지 서로 다른 시험**으로 나눈다.

1. **계산 전용 재생:** 함선·포구 변환·생존·광선 시작/종료·피해 시각을 미리 생성한 불변 입력을 모든 후보에 같은 틱 순서로 공급한다. 알고리즘 결과가 이후 입력을 바꾸지 않게 하므로 비교 작업량이 동일하다. 후보 생성·결산 자체의 비용과 정확성 비교가 목적이다.
2. **실제 게임 통합:** 선택한 동일 초기 배치·명령·데이터·시드에서 네 후보를 각각 별도 실행한다. 실제 움직임·격침·후속 발사 수는 결과에 따라 달라질 수 있으므로 사건 수와 생존 수를 함께 보고한다. 렌더링·포탑·UI·공간 구축이 포함된 사용자 체감 확인이며 계산 전용 결과와 합산해 단일 속도비를 내지 않는다.

행렬: 기준 16척 실제 LC01, 계산 전용 16/32/64/128척; 판정 광선 0/16/64/256 포구; 방향 축 정렬/대각선, 사거리 짧음/김, 분산/밀집, 차폐 가까움/없음, 1/2/4포구 및 시작이 같은 틱/다른 틱을 포함한다. 일부 조합만 먼저 돌리는 경우 빠진 조합을 명시한다. 포구 수는 실제 피해 주기에 도달한 광선 수와 활성 광선 수를 별도 기록한다. 셀 크기 h는 동일 기본값과 대안 2개를 별도 시리즈로 시험한다.

동일 코드 리비전·데이터 해시·브라우저 버전·장치·해상도·렌더 방식·셀 크기·시나리오 시드·동일 시뮬레이션 틱 수를 기록한다. 초기 제안: 준비 300틱, 측정 1800틱, 후보마다 5회 이상 반복하며 매 반복 후보 순서를 회전한다. 실제 경과 시간과 완료 틱을 기록해 느린 실행에서 고정 실제 시간 종료로 작업량이 줄지 않게 한다. warm-up·계측을 포함/제외한 값을 구분하고, 측정 코드가 핫 경로를 바꾸는 영향도 확인한다. 자동 시작 값은 실측 상황에 따라 수정할 수 있으며 수정 이력을 남긴다.

기존 지표를 유지한다: 실제 경과/게임 경과, 프레임 간격 중앙값·p95, 버린/밀린 고정 틱과 최대 누적 지연, 활성·생존 함선 수, 실제 발사/피해 사건, 레이 후보·자기 안전 검사 횟수 및 처리 시간. 여기에 각 고정 틱의 총 시뮬레이션 시간 p50/p95/p99/최대, `B`, `S`, 등록·방문 셀, 원시/중복 제거 후 후보 쌍, 선분–구 검사 횟수, 첫 차단·피해 건수, 정확성 불일치, 인덱스 생성/후보 생성/중복 제거/정밀 검사/첫 차단 결산/피해 반영 시간, 할당량·GC를 추가한다. `performance.now()`의 해상도와 중첩 측정 여부를 기록하며 하위 구간 합계를 중복 합산하지 않는다. 브라우저에서 할당·GC를 정확히 수집할 수 없으면 `미수집`으로 표기하고 추정치를 사실처럼 적지 않는다.

같은 장면의 p50/p95와 반복별 분포를 제시하고, `개선율=(기준−비교)/기준×100`을 적용한다. 기준 0이거나 틱 수/사건 수가 다르면 해당 비율을 계산하지 않는다. SwiftShader의 렌더 수치는 실제 GPU 성능이 아니며, 기존 조사와 환경·작업량이 다르면 과거 수치와 직접 개선율을 내지 않는다.

### R9.1 측정 정의·기록 계약 — 2026-11-25

기록용 [CSV](../investigations/sustained-ray-benchmark.csv)는 **1행 = 한 시나리오·한 알고리즘·한 반복 실행**이다. 현재 헤더만 있으며 수행 결과·측정값을 미리 기입하지 않았다. 구현과 계측이 끝나기 전에는 이 표를 성능 결과로 사용하지 않는다. 측정 원본은 `raw_data_ref`의 경로/식별자와 `input_hash`·코드 변경 상태로 연결한다. 동일 재생 입력의 해시·틱 범위가 다르면 비교 쌍이 아니다.

**실행 순서:** 실행 전 장치/브라우저·전력/렌더 환경과 HEAD·미커밋 diff 해시·입력/자산 해시를 확정한다. 각각 동일 입력의 E 정확성 대조를 통과한 A0/A1/B/C/D-noearly/D-early를 비교한다. 시작 순서는 반복 1에서 A0→A1→B→C→D-noearly→D-early, 반복 2부터 한 칸씩 순환해 앞 순서가 고정적으로 유리해지지 않게 한다. 각 후보는 새 독립 실행에서 **준비 300틱 이후 측정 1800틱**, 같은 시나리오 최소 5회 반복한다. 모든 후보가 측정 범위 시작 전 같은 시작 상태를 갖도록 재생한다. 워밍업 중의 틱은 원시 입력·상태 진행에 포함하되 시간 분포·사건 집계에는 넣지 않는다. 무효 설정·예외·탭 백그라운드 스로틀·페이지 재로딩·미완료 틱이 생긴 실행은 지우지 말고 `invalid`와 이유를 남긴다. 실패 재시도는 별도 `run_id`이며 원본 반복을 덮어쓰지 않는다.

**시간 창과 계산:** `wall_ms`는 측정 첫 틱 직전부터 마지막 틱 종료까지 단조 시계 `performance.now()` 차이, `sim_ms`는 완료 측정 틱 수×고정 틱 길이×1000이다. 계산 전용은 렌더 대기 없이 동일 입력 틱을 수행하므로 실제/게임 시간 비율은 처리율일 뿐 프레임 속도가 아니다. 통합 시험의 프레임 간격은 같은 측정 창의 연속 `requestAnimationFrame` 시각 차이이며 숨김/스로틀 상태는 기록·제외한다. `dropped_ticks`는 구현에서 실제로 버린 틱만, `backlog_peak_ticks`는 아직 처리되지 않은 대기 틱의 최대치를 기록하고 구분한다. 데이터가 없는 측정값은 **빈 셀**, 실제 0은 숫자 `0`이다. 프레임·GPU·GC 관측이 불가능할 때 0으로 대체하지 않는다.

각 틱의 총 시뮬레이션 시간과 프레임 간격은 모든 측정 틱/프레임의 표본에서 정렬 후 `ceil(p*N)-1` 인덱스의 nearest-rank 방식으로 p50/p95/p99를 구한다. 표본 수가 0이면 전부 공란이다. `sim_tick_*_ms`는 틱 전체, `ray_tick_*_ms`는 인덱스 구축부터 피해 결산까지의 광선 처리 전체이며 판정 광선 0개 틱도 포함한다. 해당 틱의 광선 수가 0인 비율은 `due_ray_zero_ticks`로 기록하므로 평균·백분위 해석 시 함께 본다. `frame_samples`와 `sim_tick_samples`는 표본 크기다. `sim_max_ms`와 `ray_max_ms`는 틱 표본의 최대, `frame_p95_ms`는 렌더 간격의 95백분위다.

**광선 처리 단계의 배타 시간:** 같은 단조 시계와 계측 설정에서 틱마다 `ship_index_ms`(이동 후 함선 인덱스 생성), `ray_index_ms`(B/C 광선 셀 등록), `candidate_ms`(셀 방문·후보 생성), `dedup_ms`(중복 제거), `intersection_ms`(공통 선분–구 정밀 검사), `first_hit_ms`(광선별 첫 대상 결산), `own_safety_ms`(포구 자기 구조 안전), `damage_apply_ms`(함선 피해 합산·실드/HP 적용)으로 나눈다. CSV의 각 `*_total_ms`는 측정 창 전체의 **배타 누적 시간**이다. 루프 안 교차 검사처럼 다른 단계와 중첩될 때는 중첩분을 빼거나 별도로 계측한 뒤 배타값을 만들고, 배타 구분 불가하면 해당 단계 셀을 공란으로 둔다. `ray_pipeline_total_ms`는 광선 처리 전체를 직접 재며 나머지 단계 합보다 크거나 같을 수 있다. 부분 시간 합을 전체 틱 시간과 중복 합산하지 않는다. 세분 계측으로 핫 경로가 바뀌는 비용은 `instrumentation`에 `full`/`minimal`로 구분하고 같은 시리즈를 별도 비교한다.

**수량과 정확성:** 각 `*_total`은 측정 틱의 합이다. `ship_cells_total`은 구축한 함선 셀 엔트리(동일 함선의 다중 셀 포함), `ray_cells_total`은 광선 셀 등록 엔트리(B/C, A/D는 해당 없으면 공란), `visited_cells_total`은 후보 조회 중 실제 방문한 셀 수다. `candidate_pairs_raw_total`은 중복 제거 전 생성된 쌍, `candidate_pairs_unique_total`은 제거 후 공통 정밀 검사 대상으로 전달된 쌍, `intersection_tests_total`은 실제 선분–구 검사 수다. `own_safety_checks_total`·`first_hit_*`·`damage_events_total`은 각 처리 횟수다. 활성 광선·피해 시각 광선은 틱별 p50/p95/최대, 생존 함선은 시작/끝을 기록한다. D가 조기 종료로 후보를 덜 검사해도 전수 참조와 첫 차단이 같아야 한다. 후보 통계 기준이 구현상 다르면 `notes`에 밝히고 같은 이름의 수치를 임의로 재해석하지 않는다.

`correctness_status`는 `not_run/pass/fail`, `mismatch_total`은 E 대비 광선별 차단 유형·첫 함선 ID·t 공차·사건 틱 또는 함선 상태 중 하나라도 다른 **고유 비교 사례 수**다. 0건인 `pass`와 측정을 하지 않은 `not_run`을 구분한다. 경계 t 공차 `1e-9`, 숫자 오류·버퍼 초과·후보 누락은 실패로 남긴다. `status=completed`는 목표 틱 완료를 뜻하며 correctness 통과를 뜻하지 않는다. 계산 전용은 원칙적으로 E 대조를 같은 입력의 별도 검증 실행에서 진행하고, `correctness_ref`에 입력 해시·검증 결과 참조를 연결한다. E 검사 시간은 성능 후보의 처리 시간에 포함하지 않는다. 통합 시험은 동일 명령·시드 결과와 사건 로그를 비교하되 동작이 달라지면 사건 수 및 차이를 기록하고 같은 작업량 개선율을 주장하지 않는다.

**비교·보고:** `run_id`는 유일, `series_id`는 환경/코드/입력 세대, `scenario_id`·`seed`·`input_hash`는 후보 간 동일 장면 연결, `repeat_index`와 `order_index`는 반복 및 순서를 뜻한다. 비교 기준은 **동일 시리즈·동일 시나리오·동일 반복의 A0**이며 A1은 정규화 참고다. `improvement_ray_p95_pct=(A0.ray_tick_p95_ms−candidate.ray_tick_p95_ms)/A0.ray_tick_p95_ms×100`이고 기준이 0, 누락, 정확성 실패, 입력/완료 틱·계측 방식 불일치면 공란이다. 프레임 p95 개선율은 통합·동일 환경과 충분히 유사한 작업량에서만 별도 계산한다. 반복별 값을 먼저 기록한 후 중앙값과 범위(최소~최대)를 보고하며, 작은 5회 표본을 신뢰구간으로 단정하지 않는다.

`ray_tick` 비교율은 알고리즘별 서로 다른 발사/피해 시각을 허용하지 않는 계산 전용 재생에 우선 사용한다. 샘플별 검증 조건은 동일 입력 해시·틱·광선 상태·후보 공차·자기 구조 검사 정책을 포함한다. 실제 게임에선 광선/격침 수가 달라질 수 있으므로 광선 처리 시간만 비교할 때도 `due_rays_total`, `damage_events_total`, `ship_alive_end` 차이를 함께 표시한다.

**CSV 열 묶음:** 식별/실행 (`run_id`, `status`, `invalid_reason`, `run_mode`, `algorithm`, `baseline_algorithm`, `series_id`, `scenario_id`, `seed`, `repeat_index`, `order_index`, `started_at_utc`), 환경/재현 (`code_revision`, `dirty_diff_hash`, `input_hash`, `asset_hash`, `browser`, `hardware`, `render_mode`, `viewport`, `instrumentation`, `raw_data_ref`, `correctness_ref`), 입력 (`cell_size`, `ship_count_initial`, `ray_count_config`, `ray_length`, `ray_radius`, `ray_interval_ticks`, `ray_duration_ticks`, `distribution`, `direction`, `occlusion`, `warmup_ticks`, `requested_ticks`), 완료/정확성, 시간 분포, 광선·함선·후보 수, 단계별 배타 누적 시간, 할당/GC, 비교율·비고 순이다. 실제 열과 단위는 CSV 헤더를 기준으로 하고, 확장 시 버전 열과 이 설명을 함께 갱신한다. UTF-8 BOM CSV이며 초안의 빈 행은 측정 0으로 해석하지 않는다.

### R10. 구현 순서와 선택 기준

1. R1/R2의 지속 포구 상태·공통 판정·전수 참조 E와 테스트 입력, 광선 시각 표현을 구현한다. 기존 실탄 사건과 CSV의 미지정 유형 상태를 보존한다. **표현용 객체 수와 판정 수를 분리**한다.
2. 기존 A0를 연결하고 정규화 A1, 함선별 B, 공통 셀 C, D-noearly와 D-early를 동일 API `resolve(snapshot,dueRays)→firstResults,stats`로 구현한다. 평가 모드 선택은 개발용이며 플레이어 전술 설정을 늘리지 않는다.
3. R8의 R01~R10 전체와 전수 E 대조를 통과한 후 계산 전용 재생을 수행한다. 한 후보의 불일치는 로그와 재현 입력을 남기고 성능 순위에서 제외한다.
4. 실제 FBX·실제 GPU/화면 및 기존 조준·아군 차폐·실드·정지/재개 회귀를 수행한다. 고정된 틱 수와 전투 사건 수를 표시한다.
5. 함선 주도 조건을 충족하는 B/C 중 정확성 통과 후보의 p95·최대 틱·메모리·밀집 상황을 비교하고, D와의 차이를 함께 제시한다. 작은 성능 차이에서는 구조·유지 비용과 사용자 의도도 고려한다. 광선별 D를 선택해야 할 만큼의 비용 차이가 있으면 그 책임 차이를 사용자에게 설명해 결정한다.

게임 설정은 `effect_type=RAY`, 공통 `damage_per_round`, `ray_duration_sec`, `ray_interval_sec`, `cooldown_sec`를 사용한다. 초 단위의 고정 틱 환산·검증과 로더 이관은 구현 시 처리한다. 이 절은 설정값이나 무기 유형을 사용자 대신 확정하지 않는다.

## 7. 고정 틱·득점·전환

초기 구현 제안: 고정 틱 `dt=1/60초`, 전투 구간 30초. 값은 밸런스 미결. 명시적 순서:

1. 유효 준비 명령을 받아 이전 확정 상태를 읽는다. `RUNNING`이 아니면 시뮬레이션 틱을 진행하지 않는다.
2. 틱 시작 생존 위치·자세를 스냅샷으로 만들고 함대 기준점·슬롯·근접 후보를 이용해 함선 이동 결과를 별도로 확정한다.
3. 이동 후의 단일 스냅샷으로 3D 공간 자료를 구성/갱신한다. 모든 무장·사선은 같은 스냅샷 버전을 사용한다.
4. 활성 무장의 표적 후보·각도·쿨다운을 일괄 갱신하고 확정 포구 변환 및 `ShotCandidate`를 산출한다. 조준/타게팅은 별도 주기로 나눌 수 있으나 누적 시뮬레이션 시간과 실제 속도를 유지하고 결과 나이가 발사 조건과 어긋나면 재검증한다.
5. 포구별 자기 구조와 공간 후보에 대한 레이 교차를 수신 후보 관점에서 평가하고 attack별 첫 차단을 결산한다. 보류는 사건/탄/재장전 없음. 유효 적 명중의 사건을 확정한다.
6. 같은 스냅샷의 공격을 함선별로 모아 피해를 동시에 반영하고 격침을 확정한다. 그 후 구역에 포함된 실제 생존 함선의 양측 수를 센다.
7. 득점 틱이면 모든 구역·양측의 점수를 동시에 합산한다. `d=clamp(P-E,-C,C)`, 각 진영은 `b×multiplier×max(±d,0)`를 얻는다. 현재 보유 점수의 목표 도달을 판정한다. 동시 달성은 높은 현재 점수, 동점 무승부가 v2.2 권장 임시안이다.
8. 결과가 없으면 남은 구간 시간을 차감하고 0에서 준비로 전환한다. 점수 목표와 구간 종료가 같은 틱이면 점수 결과가 우선. 구매·재기 불능 판정은 3단계 이전에 추측하지 않는다.
9. 확정 이벤트와 읽기 전용 렌더 상태를 교환한다. 화면 프레임·FX가 틱 횟수나 득점을 좌우하지 않는다.

수동 정지 후 남은 구간 시간 보존, 구간 종료 후 새 구간 부여는 시제품 제안이며 UX 검증 대상이다. 준비 단계 중 현재 HP·재장전·명령·득점 누적분, 채택한 시간 모델의 미완료 공격/FX를 고정한다. 기존처럼 초과 부하에서 틱 시간을 버릴 경우 실제 진행 틱만 게임 시간을 늘리고 버린 시간/횟수를 관측한다. 같은 결과 재현 시험은 벽시계 시간보다 **동일 완료 틱·초기 상태·시드·이벤트 순서**를 비교한다.

## 8. UI·렌더·에셋 연결과 기존 코드 처리

기존 카메라, 2단계 목표 입력, 미니맵, 함대 선택/순서/간격 UI는 가능한 범위에서 유지한다. 시뮬레이션 API는 준비 명령 검증/확정, 시작·정지, 읽기 전용 스냅샷과 이벤트를 제공한다. UI는 숫자 입력을 요구하지 않으며 HP·양측 점수·구역 상태·발사 보류 이유는 정보 표시다. 개발 진단은 게임 UI와 분리하고 미구현 기능을 완성된 것처럼 노출하지 않는다.

모델 어댑터는 확정 shipId·자세·무장 각도와 FxEvent를 화면 객체에 반영한다. FBX 모델이 없거나 해시/노드가 맞지 않으면 해당 모델/무장의 상태와 이유를 표시하고 임의의 포구에서 공격하지 않는다. 에셋별 공동 불변 변환 및 간단 형상은 로드/빌드 시 공유하되 인스턴스 각도·상태는 독립적이다. 종속 모델의 축/접합 검증 상태는 `ship-rigging.md`와 분리해 이행 기록을 남긴다.

기존 `web/simulation.js`의 MOVE·격자·슬롯, `web/main.js`의 UI·렌더러는 기능별 검증 후 재사용할 수 있다. 기존 `battleCombat`, `combatTick`, 포탑 후보 노드 임시 변경, 탄별 전체 검색은 참조/비교 대상이며 새 계약의 기본 경로로 그대로 두지 않는다. 기존 시제품과 미커밋 변경을 지우거나 기능이 완성된 것으로 취급하지 않는다. 새 코드·분리 파일의 이름은 구현 때 결정한다. 외부 FBX는 기존 저장소 밖 에셋·라이선스 규칙을 따른다.

## 11. 설계 검토 시 결정할 항목

1. 포구 레이 공격의 시간 모델: 즉시 확정, 예약 지연, 도착 재검사, 구간별 비행 중 무엇을 기본 무장으로 사용할지. 기획의 비행 중 포탄·차폐와 달라지는 정도를 확인한다.
2. 여러 시각 탄에 대응하는 실 공격 사건·피해·정확도 단위. 포구별 독립 차폐, 연장포와 일제 사격의 의미를 정한다.
3. 발사 후 아군 진입과 아군 피격/차폐, 허공 사격, 같은 틱 우선순위, 중립/잔해의 처리.
4. 실제 게임에 채택할 회전 간섭 R0/R1/R2, 허용하는 시각 오차와 포구/피격 형상. 사용자 확인 0°는 전체 자세 승인이 아니다.
5. 후보 검색 셀 크기·근사 재평가 주기, 집계/사선 반경, 환경별 성능 예산. 실제 측정 전 수치를 확정하지 않는다.
6. 필요 시 Worker·C++/Wasm 도입 경계와 비용. 현재는 웹 JS/three.js이며, 데이터 정리만으로 Unity DOTS/Burst가 동작하는 것은 아니다.

### 12.1 책임과 데이터

| BoltVisualSpec | typeId, coreDiameter, outerDiameter, length, duration | 유형별 불변 시각 규격. 전투 수치와 별개 |
| BoltSpawnRequest | battleGeneration, eventId, tick, typeId, team, origin, impact | 확정 Bolt 포구당 시각 요청 1건, 값 복사 |
| ActiveBolt | 요청 ID·유형·진영·양 끝점·시작 시각 | 표시 시스템 소유, 종료 시 반환 |
| EngineVisualState | shipId+generation, anchorId, world pose, stage, strength, dimensions | 생존 함선의 엔진 표식별 지속 슬롯 |
| TrailHistory | shipId+generation, anchorId, 위치·시간 샘플 | 표식별 제한된 월드 좌표 링 버퍼 |
| RAY | 기존 포구별 조사 상태 | 별도 지속 효과, Bolt 풀에 합치지 않음 |

필드는 논리 계약이며 파일 배치와 JS 배열·TypedArray·AoS·SoA는 측정 후 정한다. 무기 유형 ID를 무장 → 발사 후보 → 확정 결과 → 표시 요청으로 진영과 함께 전달한다. ID는 경기 세대와 함께 구분하고 다중 포구는 서로 다른 발사 ID를 쓴다. 시각 요청의 중복 ID는 한 번만 수용한다. 좌표는 이동하는 노드를 참조하지 않고 확정 틱의 값을 복사한다. 무효 유형·진영·좌표는 해당 표시만 거부하고 사유를 집계하며 이미 확정된 피해와 쿨다운을 되돌리지 않는다.

### 12.2 Bolt 규격과 시각 표현

함선 가장 긴 축을 2.2 월드 단위로 정규화한 **초기 제안**이다. LC01 포신 6개의 메시 투영 폭은 약 0.0192, LC05 중앙 포신은 약 0.0463이다. 포구 내경 실측이 아니며 다른 함종은 같은 정규화 가정일 뿐 현재 게임에서 검증하지 않았다. LC01 포신은 비슷한데 BOLT01~03을 사용하므로 유형 구분을 위해 02·03은 포신 외형보다 의도적으로 크다.

| 규격 | BOLT01 | BOLT02 | BOLT03 | BOLT04 |
|---|---:|---:|---:|---:|
| 중심부 지름 | 0.020 | 0.025 | 0.035 | 0.050 |
| 색상 영역 포함 지름 | 0.030 | 0.038 | 0.053 | 0.075 |
| 길이 | 0.25 | 0.35 | 0.50 | 0.70 |
| 표시 수명 현재 시제품값 | 0.65초 | 0.85초 | 1.10초 | 1.40초 |

지름은 반지름이 아니고 희미한 Glow는 외곽 지름에서 제외한다. 아군은 청백 중심→파랑 테두리→투명, 적은 적백 중심→빨강 테두리→투명으로 표현한다. Bolt 01의 색이 흰 중심이나 Bloom에 묻히지 않도록 실제 카메라에서 조정한다. 공격·명중은 지속 엔진·항적보다 우선 읽히게 한다.

출발~명중 거리 D, 정규화 방향 d, 유형 길이 L에 대해 게임 시간 진행률 u=clamp((t-start)/duration,0,1), 선두 s=uD, 후미 max(0,s-L)의 구간을 그린다. 출발점 뒤와 명중점 너머로 늘어나지 않으며 D가 유한 양수가 아니면 표시를 거부·계측한다. 유형별 고정 수명에서는 시각 속도가 거리에 따라 달라진다. 이것은 즉시 판정의 표현이며 실제 비행·충돌이 아니다. 표시 크기에서 전투 충돌 반경을 유도하지 않는다.

### 12.3 요청·시간·수명 계약

확정된 각 틱의 요청을 렌더 소비 시점까지 순서대로 누적한다. 렌더는 한 번만 소비하고 발생 게임 시각을 보존한다. 0틱·다중 틱 프레임에서도 마지막 틱 데이터만 읽거나 미소비 큐를 덮지 않는다. 소비 시 이미 수명이 끝났으면 늦게 재생하지 않고 expiredBeforeRender로 집계한다. 최소 표시를 강제해 피해 시간을 바꾸지 않는다.

수동 일시정지 중 게임 시간·Bolt·엔진·항적은 정지하고 재개 시 보존한다. 현재 수동 정지와 라운드 준비는 모두 PREPARATION이므로 phase만으로 초기화하지 않는다. 라운드 종료 후 준비에서는 남은 효과를 정지·보존하고 게임 재개 후 소멸시키는 임시 정책이다. RESULT는 새 요청 없이 표시를 정지·보존한다. 새 경기·명시적 재설정·렌더러 해제 시 큐·슬롯·항적을 정리하고 경기 세대를 갱신한다. 렌더 지연, 준비 전환과 수동 정지가 겹치는 경우도 검증한다.

### 12.4 엔진과 비행운

시제품 속도 지표는 r=clamp(|ship.velocity|/ship.forwardSpeed,0,1)이다. 이는 함선별 최대 전진 속도 대비 기동 수준이지 함선 간 절대 속도나 실제 추진 출력이 아니다. 옆·후진 제한이 다르며 기준 속도가 유효하지 않으면 표시를 끄고 진단한다.

- 정지는 r ≤ 0.02에서 기본 발광만 유지하고 신규 링·항적을 끄는 후보이다. 이동 1·2·3단계의 링 수는 정확히 1·2·3개다. 단계 경계와 상승·하강 히스테리시스는 화면 시험 전 미결이다.
- 링은 단계 전환에서 짧게 페이드하고 분사 길이·밝기와 항적 목표 길이는 부드럽게 변화시킨다. 1단계에서 신규 항적은 없고 2단계부터 짧게, 3단계가 가장 길다. 감속 시 기존 항적은 수명에 따라 사라진다.
- FX_Engine_*는 위치 표식이며 노즐 직경을 포함하지 않는다. 표식별 방향과 크기는 실제 모델 검수 후 설정한다. 엔진 개수만으로 직경을 확정하지 않는다. 누락 표식·무효 자세는 해당 표식만 건너뛰고 진단한다.
- 함선별 또는 엔진 표식별로 월드 좌표와 게임 시간을 기록한다. 선회 시 기존 점은 함선과 함께 회전하지 않는다. 이동 거리나 최대 시간 간격으로 점을 추가하고 중복점·최대 수·길이·수명을 제한한다. 순간 이동/재배치는 경로를 끊는다. 실제 샘플 간격, 끊기 기준과 2/3단계 길이는 미결이다.
- 격침·제거 시 엔진과 링은 비활성화하고 기존 항적은 새 점 없이 자연 소멸한다. ID 세대가 바뀌면 이전 경로와 연결하지 않는다.

### 12.5 렌더 배치와 용량

유형 규격과 물리적 풀 분리는 별개다. 비교 후보 A는 공통 지오메트리와 진영별 재질을 공유하는 Mesh 풀, 후보 B는 진영별 InstancedMesh 배치에 유형별 크기·개별 변환을 적용하는 방식이다. 같은 형상에 네 개 독립 에셋이나 풀이 필수는 아니다. B에서는 활성 슬롯을 연속 배치하고 제거 시 마지막 슬롯을 옮기며 ID→슬롯 매핑을 함께 수정한다. 행렬 갱신 표시, 인스턴스 수, 컬링 경계, 색상 셰이더 및 투명 정렬을 검증한다. 공유 재질의 진영 변경이 다른 효과를 오염시키면 안 된다.

풀·버퍼 초기 용량·증분·최대치는 실제 동시 발사와 수명을 측정해 정한다. 이전 제안의 64/256은 확정값이 아니다. 부족 시 최대치까지 확장하며 재할당 때 활성 데이터와 매핑을 보존하고 교체된 GPU 자원을 해제한다. 최대치 또는 할당 실패 시 **시각 요청만** 생략한다. requested, accepted, rendered, expiredBeforeRender, droppedCapacity, invalid, peakActive를 집계한다. 권위 전투 사건의 포화는 이 문서 전투 오류 정책을 따른다. 공유 자원은 효과 반환 시 해제하지 않고 렌더러 종료 시 정리한다.

인스턴싱은 드로콜 감소 후보이지 전체 성능 보장이 아니다. CPU의 행렬 작성·GPU 업로드·투명 오버드로·Glow·항적·컬링 및 할당을 함께 측정한다. 표시 예산·LOD는 전투 판정 수를 바꾸지 않는다. 원거리에서는 진영과 방향을 우선 남기고 Glow·항적 밀도를 줄이는 후보를 검토한다.

### 12.7 2026-11-26 시제품 구현 기록

Bolt 유형과 진영을 발사 결과에서 시각 요청으로 넘기고, 게임 시간 기준 유형별 0.65/0.85/1.10/1.40초 효과를 진영별 InstancedMesh와 공유 셰이더로 표시한다. 엔진 표식별 속도 단계·히스테리시스, 분사와 1~3개 링, 2/3단계의 월드 위치 이력 항적을 연결했다. 효과 종류별 임시 최대 인스턴스 수는 4096이며 측정에 근거한 예산이 아니다. 항적은 선 표현이며 폭 테이퍼·거리 기반 LOD는 미구현이다. 노즐 크기와 방향, 단계 경계, 길이는 실제 모델에서 보정할 임시값이다.

검증: JavaScript 구문 검사, 속도 단계 경계 9건 및 배치 확장 중 5개 인스턴스 보존 계산 확인. 브라우저에서 LC01 모델 로딩, 양측 이동 중 엔진·항적 표시, 교전 진행 및 일시정지 전환을 관찰했고 해당 관찰 시 콘솔 오류가 없었다. Bolt 01~04 각각의 실제 화면 가독성·색상과 셰이더 품질, 정확한 링 개수·모든 단계·격침·포화·장시간, 다른 함종, 동일 전투 결과 회귀 및 실제 GPU 전후 성능은 검증하지 않았다. 설계의 A/B 비교, 모든 FX 수용 조건 및 효과 완성 판정은 남아 있다.
