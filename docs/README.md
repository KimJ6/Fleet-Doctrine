## 충돌 해결과 상태 구분

1. 사용자의 최신 명시적 결정과 승인된 변경이 우선한다. 게임 규칙은 최신 통합 기획이 기준이며, 기획 내부의 확정·권장·임시·미결을 유지한다.
2. 구현 계획은 기획을 실현하기 위한 설계다. 참고 설계와 조사 기록은 제안 또는 관찰이며 기획을 자동 변경하지 않는다. 이전 판과 부속 이력의 당시 우선순위는 현재 통합본을 대체하지 않는다.
3. 실제 동작은 현재 코드·실행 조건을 확인한다. **기획 채택, 설계, 구현, 테스트 통과, 수동 관찰, 성능 측정**을 구분하며 코드나 테스트의 존재만으로 통과를 주장하지 않는다.
4. 모델별 정책과 게임 규칙이 만나는 부분은 양쪽의 적용 범위를 명시한다. 기획이 미결인 아군 피해 등은 구현 임시 선택을 확정 기획으로 기록하지 않는다.

현행 조우·진형·기동은 2026-11-27 [조우 정책 재설계](design/Fleet-Doctrine-Encounter-Policy-Redesign.md)를 우선한다. v2.2 및 기존 구현 계획의 이전 전술 설명은 이력으로 보존하며 그 외 규칙에 대한 효력은 유지한다.

## 작성·변경 규칙

- 이름은 영문 소문자와 하이픈을 쓰고 문서 역할을 드러낸다. 버전이 의미 있는 확정 기획의 과거 판은 파일명에 버전을 둔다. 조사 기록은 `issue-번호-주제.md`를 사용하고 해당 이슈를 연결한다.
- 각 문서는 제목·상태·작성 또는 갱신일·범위·상위/관련 문서를 명시한다. 기존 원문 날짜와 변경 이력은 보존하고 정리 날짜를 원래 작성일로 바꾸지 않는다.
- 같은 규칙의 소유 문서를 정하고 다른 문서는 링크한다. 과거 판을 유지하는 경우 이력임을 상단에 표시한다. 본문 통합 시 고유한 테스트 ID·근거·미결과 변경 이력을 잃지 않는다.
- 문서 이동·이름 변경 시 저장소의 Markdown 링크, 실행 안내, 코드에 포함된 생성 문구를 함께 수정하고 로컬 링크와 검색 결과를 확인한다. 외부 이슈·옛 커밋 링크는 과거 상태일 수 있음을 고려한다.
- 조사 문서는 실행 환경·시나리오·측정 방법·원자료 또는 기록 위치·결과·한계를 남긴다. 조건이 다르거나 측정이 불완전하면 수치를 직접 비교하거나 FPS로 환산하지 않는다.
- 문서 갱신 시 관련 구현 상태를 코드와 비교하고 확인하지 못한 사항은 미검증으로 남긴다. 새 기능 완성이나 모든 문서의 최신성을 목록 갱신만으로 선언하지 않는다.
